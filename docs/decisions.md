# Решения (ADR-список)

**Назначение:** реестр архитектурных решений платформы DMG. Новое решение добавляется строкой `D-NN`, старое помечается «заменено D-NN». Номера сквозные с проектом-источником, поэтому пропуски допустимы: решения проекта (процесс, документация, переход) в пакет не входят.

---

## Основа

**D-01. Манифест — единый источник истины.** Каждая доменная сущность объявляется один раз декларативным объектом (`*Def`). Из него выводятся типы, схемы, свойства базовых классов, транспорт, документация, MCP и контрактные тесты. *Почему:* сейчас одна команда описывается в 5–6 местах, связи скрыты в коде.

**D-02. Четыре оси.** Платформа (`dmg-core`, пакет приложения) → домен (пакет домена) → прикладной слой (прикладной пакет модуля, строго 1:1 с модулем домена) → входные адаптеры (UI и транспорты). См. [layers.md](./layers.md).

**D-03. Домен един, чист и синхронен.** Пакет домена содержит всю предметку и все контракты (UC, ER, Job, фасады, модули). Никакого IO; асинхронность — только `Loader<T>`. Любой слой пользуется доменом через его API, но только в рамках `dependsOn` модулей (граф модулей — DAG).

**D-04. Пакет приложения — платформа приложения.** Замыкает дженерики (пользователь, резолверы, сборка модулей), импортирует домен. Доменных сущностей не содержит: пользователь и роли — модуль домена.

## Доменный API

**D-05. Entity видят только Ar и конечные рендереры.** Все остальные (UC, ER, Job, Story, DCS, DQS, Policy, фасады, репозитории) работают только через API доменных объектов. Рендереры UI (компоненты отображения) могут работать с entity напрямую, в т.ч. для реактивности. Репозиторий работает через `Ar.restore()` / `ar.snapshot()`. Форма state в контрактах и показ полей — уточнено D-39.

**D-06. Уровни доменного API: Ar → Policy → DCS / DQS.** `DomainCommandService` (DCS) координирует несколько агрегатов с мутацией и возвращает `Result`. `DomainQueryService` (DQS) — только чтение, не зависит от транспорта. Сервисы могут принимать `Loader<T>`. Story и UseCase остаются в стандартном смысле (входной сценарий UI и прикладная операция). Между Policy и DCS — декларативные доменные правила (D-40).

**D-07. `ReadonlyAr<T>` и изоморфный домен.** Мутирующие методы Ar всегда возвращают `Result`, методы-вопросы — никогда; `ReadonlyAr<T>` выводится типом без ручного кода. Фасады, транспорт и UI получают снапшот и восстанавливают Ar локально как `ReadonlyAr`.

**D-08. UC только техничен.** Загрузить → Policy → операция домена (Ar / DCS) → зарегистрировать в UoW. Никаких доменных решений (`if` по состоянию, статусам, входу).

## Контракты и связи

**D-09. Модули и фасады — стратегический уровень.** У каждого модуля есть паспорт `ModuleDef.define` (`dependsOn`) и фасад — runtime-API модуля для других модулей (без манифеста, D-42; `Facade<M>`, D-43). Фасады возвращают `Result`.

**D-10. Ссылки вместо строк, FQN для событий.** Манифесты ссылаются друг на друга объектами. Имя события — `module.aggregate.event` (`todo.task.completed`).

**D-11. Граф L0 / L1 / L2.** L0 — карта модулей, L1 — модуль, L2 — агрегат. Каскад проходит сквозь уровни.

**D-12. Декларация + верификация.** Каждая декларация проверяется типом, рантайм-ассертом в test/dev или контрактным тестом. Правило без проверки — пожелание.

## Ошибки и сохранение

**D-13. `Result<T, E>` вместо `throw` для штатных отказов.** `throw` — только баг, инвариант, системный сбой. См. [errors-result.md](./reference/errors-result.md).

**D-14. Ошибка не знает транспорт.** У ошибки есть `code` и нейтральный `kind`; маппинг в HTTP / MCP / текст бота — в адаптерах. Ошибки зависимостей пробрасываются по ссылке через контракт фасада.

**D-15. Unit of Work в `dmg-core`.** UC регистрирует изменённые агрегаты в UoW; базовый класс после `Ok` фиксирует изменения и публикует события агрегатов. JSON-реализация не атомарна — осознанный техдолг до смены хранилища.

**D-16. Время — `Timestamp` (number, мс, UTC).** Переходные схемы читают ISO-строку, пишут число; пакетная миграция данных — забота проекта.

## Транспорт

**D-17. HTTP — JSON-команда.** `POST /api/<module>` с `{ uc, input, meta? }`; `OPTIONS` отдаёт контракт модуля. См. [transport.md](./reference/transport.md). Уточнено D-49: модуля в команде нет, его адресует транспорт.

**D-18. MCP из манифестов.** UC → tools, граф → resources. Старт: только query, dev, заданный актор.

## Вызовы, границы и проверки

**D-25. `Caller` — кто вызывает.** Четыре подтипа: `guest`, `user`, `delegate`, `system`. Def UC объявляет `callers`; домен видит субъекта (для `delegate` — замещаемого), аудит — исполнителя через meta событий. Тип и `callers` — в `dmg-core`, делегирование — модуль приложения. См. [caller.md](./reference/caller.md).

**D-28. Модуль готов к выносу в сервис.** Межмодульно — только асинхронные фасады и события по Def; один UoW — один модуль; реакции идемпотентны, публикация через outbox; `Caller`, `Trace`, конверт события и снапшот Ar сериализуются в JSON. Модулю в другом репо нужны только контракты зависимостей (`domain/<m>/contract`), не весь домен. Сервис из одного модуля — то же приложение с одним модулем в `dependsOn`.

**D-32. Архитектурные правила — в biome.** Импортные границы (ARC) — `noRestrictedImports`, остальные (DOM-01/11/12/14, ERR-01, API-02, CODE-02) — GritQL-плагины в `overrides`. Какие пути блокируются, решает проект (старый код можно исключить или перевести в `warn`). Правила проверяются тестом на фикстурах-нарушителях, поэтому ослабить правило незаметно нельзя.

**D-33. Подпути `dmg-core` по слоям.** Корень — ядро и манифесты домена (`Result`, ошибки, `F`, Def-классы, `Aggregate`, Policy): чистый код, единственное, что видит домен. `dmg-core/app` — исполнение (UC/ER/Job по Def, модуль, UoW, шина, след), `dmg-core/graph` — нормализация и граф, `dmg-core/arch` — проверки, `dmg-core/testing` — хелперы. Граница проверяется lint (ARC-02 для домена, ARC-11 внутри пакета). UI-манифесты — отдельным пакетом, не подпутём.

**D-34. Время — аргумент операции, часы — порт приложения.** Домен не читает часы: момент передаётся в операцию Ar (`create(input, at)`, `complete(at)`), `updatedAt` ставит база из того же `at`. Часы — `AppContext.clock` (`Clock`, `systemClock`); UC/ER/Job берут момент через `this.now()`, UoW — для `occurredAt`. Глобального изменяемого состояния нет: в тестах часы задаёт `testAppContext({ at })`; приложение может передать свои часы (мост к старому коду).

**D-35. Жизненный цикл агрегата — в Def.** Переход объявляет `from`, `to` и `rejects` (ошибку для каждого статуса вне `from`, полноту проверяет компилятор, принадлежность группе агрегата — MAN-12). Ar меняет статус только через `transition(op, at, apply)`, база возвращает отказ из Def и ставит `to`; `change` статус не трогает. Граф L2 получает операции с их отказами без разбора кода методов.

**D-36. Версия агрегата — оптимистичная блокировка.** `BaseEntityFields.version` растёт с каждой мутацией Ar (записи без поля читаются как 0, миграция данных не нужна; так же запись без `updatedAt` читается как `updatedAt = createdAt` — фолбэк в `def.state` агрегата, поэтому сырые данные разбираются `<Agg>ArDef.state`, а не экспортированной схемой). Репозиторий при `save` сверяет версию в хранилище со `storedVersion` агрегата и при расхождении бросает `VersionConflict`; UoW превращает его в базовую ошибку `VERSION_CONFLICT`; события публикуются только у агрегатов, записанных до сбоя (они не откатываются, D-15). Новый агрегат (из `create`, база — `Aggregate.newState`, D-43) отличается от записи версии 0: `create` с занятым uuid — конфликт, старая запись не перезаписывается. Атомарность чтения-сверки-записи — забота хранилища; база `VersionedRepository` выполняет `save` под замком `Lock` в процессе (с трека `dmg-core-oop`). Откат уже записанных агрегатов UoW не делает (D-15).

**D-37. Внешний модуль — контракт без реализации.** Модуль, реализованный вне приложения (ещё не переведённый код или другой сервис, D-28), описывается `ModuleDef.define({ external: true })` в своём `contract.ts`: агрегаты с событиями, фасад, Def UC без реализации (D-42), без ER/Job. На него можно ссылаться в `dependsOn` и подписываться на его события; MAN-06 считает их опубликованными внешней стороной. События старого кода доставляет мост приложения (старое имя → Def, перевод payload, проверка схемой, сбой — в production `warn`). При переводе модуля на Def `external` снимается, контракт остаётся.

**D-38. ~~Фасад модуля — только по потребителю.~~ Заменено D-42** (фасад без манифеста). Модуль объявляет `defineFacade` только когда фасад нужен другому модулю (вызов из UC/ER/Job по `calls`, ARC-04); спекулятивное API не заводится.

**D-39. Доступ к state: решение — только Ar, форма — в контрактах, показ — в рендерере.** Уточняет D-05. Разводятся три вида доступа к state агрегата:
- **решение** (ветвление по полям) — только Ar: методы-вопросы и операции; остальные (UC, ER, Job, Story, Policy, доменные правила, DCS, DQS, фасады) получают `ReadonlyAr` и спрашивают его;
- **форма** (схема) — Def контрактов своего модуля (вход и выход UC, payload событий, проекции DQS, фасад) выводят схему из state (`v.pick`/`v.omit`), а не копируют поля вручную; чужой модуль state не импортирует;
- **показ** (чтение полей для отображения) — только рендереры UI; Story передаёт данные рендереру и полей для решений не читает.

Репозиторий — `restore`/`snapshot` и ключи хранения; тесты и фикстуры строят агрегат через `create`/`restore`. Геттер на поле Ar — только для идентификаторов (`uuid`, связи): данные, нужные контракту ошибки или выхода, отдаёт метод Ar, который строит этот контракт (Ar владеет ошибками своей группы). Lint DOM-01 разрешает импорт `…/state` файлам Def контрактов своего модуля.

**D-40. Доменное правило — декларативно, без субъекта; Policy — только права субъекта.** Критерий выбора — **участвует ли в ответе субъект** (caller), а не число агрегатов:
- **Policy** — «может ли этот субъект?»: контекст может содержать несколько агрегатов (владелец этой задачи и проект, в котором она лежит); отказ — `ACCESS_DENIED` (`kind: access`) с `denyMessage`.
- **Доменное правило** — «допустимо ли действие при текущих состояниях агрегатов?» (уникальность, допуск к следующему модулю): ответ не зависит от того, кто спрашивает. Объявляется декларативно по образцу `rule` — имя, `label`, `description`, ссылка на `ErrorDef` своей группы, проверка над `ReadonlyAr`/значениями — и возвращает `Result<void, Err>` с payload ошибки, а не `Decision`. Def UC ссылается на правила рядом с `policy`, правила видны в манифесте и графе.
- **Переход Ar** (`rejects` в `AggregateDef.define`) — частный случай доменного правила в пределах одного агрегата; остаётся в Ar.

DCS остаётся для мутаций нескольких агрегатов и композиции правил с операциями. Композиторы (`allOf`/`anyOf`) для доменных правил — только по потребителю.

Форма API: `DomainRuleDef.define({ name, label, description, error, check })` в группе `<A>Rules = RulesDef.define({ name, label, description, rules })`, файл `<aggregate>.rules.ts` ([manifests.md](./manifests.md) §1). Def UC — `rules: [...]` рядом с `policy`; исполняет `UseCaseFromDef` над результатом `load` после Policy (`load → Policy → rules → execute`; с D-58 — над `load` и `fetch`: `load → Policy → fetch → rules → execute`). Ошибка правила объявляется в `errors` UC явно — `ArchChecker` ловит пропуск.

**D-42. Межмодульная связь в манифестах — «UC → UC»; фасад — рантайм-граница без манифеста.** Заменяет D-38, уточняет D-09. Вызывающий `module`, ответственность фасада и рантайм-проверка `calls` — заменены D-43.
- **Связи объявляются один раз:** `dependsOn` у модуля и `calls` у UC/ER/Job — Def UC других модулей (из `dependsOn`). Граф строит рёбра «UC → UC» из `calls`; последствия вызова (агрегат, `emits`, дальше по ER) выводятся из Def вызываемого UC; command-цель — межмодульный побочный эффект, место которого выбирает владелец проекта по каждому случаю ([use-case.md](./guides/use-case.md) §1). Фасадов в манифестах и графе нет (`defineFacade`, `method`, `facade` в паспорте модуля уходят).
- **Фасад остаётся в рантайме** — граница модуля: вызывающий модуль не знает реализации владельца (in-proc сейчас, сетевой клиент при выходе в отдельный сервис — вызывающий код не меняется). Тип фасада — TS-тип в домене модуля-владельца (`<m>.facade.ts`, не Def), реализация — в его пакете.
- **Ответственность фасада** (форма заменена D-43: `Facade<M>.handle` без методов-обёрток, `ReadonlyAr` строит вызывающий): обёртка над UC своего модуля — каждый метод вызывает UC; допустимы несложные преобразования входа и выхода (собрать вход, выбрать поле, свести ответ), доменных решений нет (их делает UC и домен владельца). Выход UC, который является state агрегата (один или массив), фасад отдаёт как `ReadonlyAr<T>` (`ReadonlyAr<T>[]`) — клиент получает готовый агрегат. Ошибки метода — ошибки вызываемого UC (`Result`), фасад их не прячет и не придумывает.
- **~~Вызывающий `module`.~~ Заменено D-43.** Фасад вызывает UC от вызывающего вида `module` (его обязанность — подставить его): `from` — Def UC/ER/Job, который вызвал фасад, `origin` — исходный вызывающий; субъект (`subjectOf`) — субъект `origin`, Policy вызываемого UC проверяется. UC, доступный другим модулям, объявляет `module` в `callers`, иначе — `UNAUTHORIZED`.
- **Проверки:** `ArchChecker` — UC в `calls` из модуля в `dependsOn`, не свой; ~~рантайм — вызываемый UC отказывает (`UNAUTHORIZED`), если его Def нет в `calls` у `from`~~ (заменено D-43: типом `call`). Ревьюер — фасад без доменных решений.
- **Внешний модуль (D-37)** объявляет Def UC без реализации; приложение исполняет их адаптером над старым кодом или сетевым клиентом; при переводе модуля Def получает реализацию, адаптер уходит.

**D-43. Вызовы и граница модуля: `Caller`-классы, модуль — единственная точка входа, типизированный `call`.** Заменяет в D-42 вызывающий `module` и рантайм-проверку `calls`; остальное в D-42 в силе.
- **`Caller` — иерархия классов** (`GuestCaller`, `UserCaller`, `DelegateCaller`, `SystemCaller`) с `subject()`, `person()`, `toLog()`. Вызывающего `module` нет: межмодульный и внутренний системный вызов — один `SystemCaller(from: OperationRef, person?)`, где `from` — `{ kind, module, name }` вызвавшей операции, `person` — исходный человек (`caller.person()` пришедшего, матрёшки нет). ER и Job — без `person`. `channel` — в `Trace.channel`, не в `GuestCaller`. Подробно — [caller.md](./reference/caller.md).
- **Policy — только субъект, вызывается всегда** (`Rule.evaluate(subject, ctx)`): вид вызывающего она не знает, `delegable` нет. Вид отсекает `callers` (`UNAUTHORIZED`). Системный вызов без субъекта — явно: отдельный UC (`callers: ['system']`, `allowAll`) или переопределение `protected checkPolicy` в наследнике. Шаги `UseCaseFromDef` — `protected`: `checkCaller` → `parseInput` → `load` → `checkPolicy` → `checkRules` → `execute` → `parseOutput` → фиксация (с D-58 — `fetch` между `checkPolicy` и `checkRules`).
- **Модуль — единственная точка входа:** `ModuleFromDef.handle(def, input, caller, trace)` и `runJob`; `useCase(def)` не публичный. Транспорт и фасад ходят только через модуль.
- **Фасад** — `Facade<M>` в домене (`handle` только UC с `'system'` в `callers`, вызывающий — `SystemCaller`) и `ModuleFacade<M>` в `dmg-core/app`, обёртка над `ModuleFromDef.handle`. Свои типы фасадов модулей и методы-обёртки не заводятся; наследник `ModuleFacade` — только ради удобных методов поверх `handle`. Выход — как у UC; `ReadonlyAr` строит вызывающий (`Aggregate.readonly(state)`). В тестах — `StubFacade<M>` (`dmg-core/testing`).
- **`OperationFromDef`** — база UC/ER/Job: `now()`, `createUow(caller, trace)`, `protected call(def, input, caller, trace)` — только Def из `D['calls']` (по типу — UC с `'system'` в `callers`), через `ModuleFacades` в `deps` с `SystemCaller(this.ref, caller.person())`. Рантайм-проверки `calls` нет (тип + `ArchChecker`), `UNAUTHORIZED` без `from`. Ошибки ядра чужого UC проходят насквозь (`UseCaseErrorOf<D>`), доменные — объявляются в `errors` своего UC или переводятся.
- **Лог операций** (`OperationLog` в `AppContext`): запись `OperationRecord` (вызывающий `toLog()`, `trace`, вход, результат, события, длительность) пишет `OperationFromDef` последним шагом при успехе и отказе; `uow.commit()` возвращает опубликованные события. Хранение — реализация приложения (например, JSONL по дням), `input`/`output` с порогом размера. `caller` из конверта события удалён: аудит «кто» — через запись породившей операции (`trace.cause`).
- **Функции → объекты:** класс `Trace` (`fromRequest`, `fromEvent`, `forJob`) вместо `requestTrace`/`incomingRequestId`; `Aggregate.newState(uuid, at)` вместо `newEntity`; `Aggregate.readonly(state)` вместо `asReadonlyAr`.

**D-44. Состояние агрегата наружу — `view()`; `snapshot()` — только репозиторий.** Уточняет D-05 и D-39. `Aggregate.view()` отдаёт состояние тем, кому разрешён к нему доступ: выход UC (query), рендерерам UI, показывающим текущее состояние, и другим местам по тому же основанию. По умолчанию `view()` возвращает `snapshot()`; агрегат может переопределить его (скрыть или преобразовать поля). `snapshot()` вызывает только репозиторий (и его тесты/фикстуры) — для записи; больше никто. Данные для контракта ошибки или выхода, которые не являются состоянием, — по-прежнему метод Ar, строящий контракт (D-39).

**D-45. Вход модуля для остального кода — `contract`; state — внутри модуля.** Уточняет D-37, D-39, D-42, D-44. У модуля домена два входа:
- **`contract.ts`** — единственный вход для остального кода: другие модули (домен и прикладной слой), входные адаптеры (UI, stories), скрипты, транспорт и фронт. В нём только объявления: `<M>ModuleDef`, Def операций, которые вызывают снаружи, группы событий и ошибок, схемы и типы VO, входящие в эти Def. Классов (Ar, Policy, DCS/DQS), Def агрегатов и схем entity в нём нет.
- **`index.ts`** — API домена для своего прикладного пакета: всё, включая контракт.
- **State — внутренний.** Его видят Ar, Def своих контрактов (вывод схем, D-39) и репозиторий через `ArDef.state`. Подпути state у пакета домена нет. Остальной код получает форму данных из контракта: выход UC, payload событий, данные ошибок. Внутри модуля — `view()` (D-44). Фронт и транспорт знают только схемы контракта, поэтому смена state не ломает клиентов, пока контракт выводится тем же.
- **Домен другого модуля нужен — пополняется контракт.** Экспорт добавляется в `contract.ts` с JSDoc «кто и зачем». Так использование домена вне модуля явное (экспорт), определённое (одно место) и проверяемое (ARC-04).
- **Проверка.** ARC-04: чужой модуль из любого места (домен, прикладные пакеты, адаптеры, скрипты) — только `<domain>/<m>/contract` (в домене — ещё и только из `dependsOn`). Для модуля на Def (не `external`) нарушение блокирует в обе стороны: он импортирует чужие только через контракт, его импортируют только через контракт. Состав `contract.ts` — review.

**D-46. `Caller` и `Trace` переходят границу процесса как JSON.** Удалённый вызов фасада (модуль в другом сервисе, D-28) передаёт `caller` и `trace` в JSON: `toJSON()` у отправителя, статический `fromJSON()` у получателя восстанавливает классы. Субъект `U` едет **целиком**: он обязан быть простыми данными (plain JSON), а получатель доверяет отправителю (внутренние сервисы). Если у приложения `U` — класс, `fromJSON` принимает необязательный `revive(json) => U`. Вложенный вызов, как и раньше, — `SystemCaller(from, person)`; в JSON он несёт `person` со своим `U`. Тест «круг через JSON» охватывает все виды `Caller`, `Trace`, конверт события и снапшот Ar. Форма для лога (`toLog()`, только id) не меняется. **Внутри одного процесса сериализации нет:** in-proc фасады получают объекты как есть; `toJSON`/`fromJSON` вызывает только адаптер удалённого фасада, а тест круга гарантирует, что вынос модуля не сломается.

**D-47. Публикация — через outbox, доставка — с отсевом повторов.** UoW после записи агрегатов передаёт конверты не в шину, а в порт `Outbox` (`AppContext`); до шины их доставляет relay. По умолчанию outbox in-proc: конверт сразу публикуется в шину, поведение то же, что до D-47. Персистентный outbox — реализация потребителя. Реакции получают событие через порт `Inbox`: повторная доставка того же `eventId` той же реакции отбрасывается (in-proc реализация по умолчанию). Повтор с новым `eventId` (тот же факт, опубликованный дважды) — забота домена; для него `dmg-core/testing` даёт контрактный хелпер «событие доставлено дважды → второй раз эффекта нет».

**D-48. Def — классы с поведением.** Каждый вид манифеста — класс (`ErrorDef`, `EventDef`, `AggregateDef`, `DomainRuleDef`, `RulesDef`, `PolicyDef`, `UseCaseDef`, `EventReactionDef`, `JobDef`, `ModuleDef`; правила Policy — иерархия `Rule`), база — `Def` (`name`, `label`, `description`, `describe()`, `normalize()`), операции — `OperationDef`. DSL — `XxxDef.define(spec)`, объявленный в каждом виде (`define` базы с полиморфным `this` теряет литеральные типы); функции `define*` удалены. Поведение вида — метод его класса, а не `switch` по `dmg` в чужом коде (контрактный тест `kind-switch.test`). `Any*Def` — структурный тип публичных членов класса; у Def нет `private`/`#`, поля объявлены явно, сравнение по ссылке. Тем же принципом: индекс Def — `DefIndex`, проверки — `ArchChecker`/`Violation`, база репозитория — `VersionedRepository` (`Lock`), тестовые двойники — `MemoryLogger`/`RecordingBus`/`MemoryBus`; шаблоны генератора — классы вида в `gen`, а не в Def (Def — доменный контракт, шаблоны знают прикладной слой). Трек `dmg-core-oop` (2026-10-27).

**D-49. Def — типы клиента, команда — исполнение; модуль адресует транспорт.** Уточняет D-17, D-42 и D-43 (вход модуля `handle(def, …)` заменён на `dispatch`).
- **Команда — простые данные:** `Command = { uc, input, meta? }`, где `uc` — `name` Def UC, `meta` — `requestId`, `version`. `requestId` — одно намерение клиента: и след, и ключ идемпотентности command UC, отдельного ключа нет ([transport.md](./reference/transport.md) §2). Имени модуля в команде нет: модуль адресует транспорт (URL на бэке, Def модуля в `apiApp.dispatch`, `ModuleApi` вне процесса). Caller и `Trace` в команду не входят, их передаёт транспорт (D-46).
- **Def — источник типов и сахар клиента:** `ucDef.command(input)` → `Command<D>` с фантомным `D`, по нему выводятся `InputOf`/`OutputOf`/ошибки. Def собирает только команду и об адресе не знает.
- **Исполнение:** `apiApp` выбирает `apiModule` (`ModuleFromDef`) по адресу транспорта → `dispatch(command, caller, trace)` → UC по имени → обычный конвейер UC (D-43). Неизвестный модуль или UC → `Err` `OPERATION_NOT_FOUND` (базовая ошибка ядра, `not_found`). Восстанавливать Def из JSON на сервере не нужно.
- **Клиент in-proc — приложение:** `apiApp.dispatch(moduleDef, ucDef.command(input), caller, trace)` → типизированный `Result`; адрес — Def модуля, UC другого модуля — ошибка компиляции; Caller и `Trace` строит адаптер входа. Отдельного клиента на модуль в процессе нет: маршрутизация по адресу уже в приложении. **Клиент вне процесса** — `ModuleApi` (Def модуля + wire-транспорт): ответ — сериализуемый `Result` ([transport.md](./reference/transport.md) §1), восстанавливается по Def UC; in-proc — `Result` как есть, без JSON, форма та же.
- **Один путь для всех входов:** UI (бот, web), CLI, межмодульные фасады (`ModuleFacade`, D-43 — через команды, типизированный сахар поверх) и будущий HTTP. Вызовов `handle(def, …)` по ссылке на Def в прикладном слое и раннерах нет. Вынос модуля в сервис (D-28) решается в приложении (модуль подключается как удалённый), вызывающий код не меняется.

*Почему:* web-клиент передаёт по транспорту JSON, и бэк должен найти по нему UC. Если цепочка `apiApp` → `apiModule` строится на DTO команды, транспорты и in-proc не расходятся. Трек `command-dispatch`.

**D-50. Корень сборки — пакет приложения; раскладку по `dependsOn` делает платформа.** Уточняет D-04 и D-49 (`apiApp`).
- **Пакет приложения собирает приложение из окружения:** экспортирует класс приложения, который по `AppEnv` (простые данные: режим, каталоги, параметры хранилищ) строит `AppContext` (шина, outbox/inbox, часы, логгер, лог операций), репозитории и модули. Всё, что нужно для вызова UC, приложение отдаёт само: `ApiApp` и резолвер `Caller`.
- **Раннер — только вход:** точка входа, чтение `process.env` → `AppEnv`, транспорт (бот, HTTP, CLI), запуск и остановка (подписки реакций, расписание Job). Модули раннер не собирает, а `Caller` строит не сам, а через резолвер приложения.
- **`ApiApp` в `dmg-core/app`** — сборка и in-proc клиент приложения (`apiApp` из D-49). Приложение передаёт ему `AppContext` и фабрики модулей (Def модуля + функция `ModuleDeps → ModuleFromDef`). `ApiApp` упорядочивает модули по `dependsOn` и проверяет граф: цикл, отсутствующая зависимость или повтор модуля — ошибка сборки. Каждый модуль получает `ModuleFacades` только своих зависимостей. Дальше `dispatch(moduleDef, command, caller, trace)`, `runJob`, `subscribe()` всех реакций. Раскладку фасадов руками приложение не пишет. Внешний модуль (D-37) подключается своей фабрикой так же.
- **Резолвер `Caller` — приложения:** по идентичности из транспорта (uuid пользователя или его отсутствие) отдаёт `UserCaller` через модуль пользователей, иначе — `GuestCaller`. Канал и `Trace` строит раннер, потому что они от транспорта. Один резолвер обслуживает все транспорты.

*Почему:* без корня сборки каждый раннер собирает модули сам: сборка дублируется, а ошибку в раскладке фасадов ловит только тест. Новому проекту нужен один шаблон: `init` создаёт пакет приложения и раннер по этому решению. Трек `dmg-core-standalone`.

**D-51. Вызов от корня сборки — `OperationRef.kind: 'app'`.** Уточняет D-50 и D-43.
- Приложение само вызывает UC модулей не от имени пользователя: резолвер `Caller` (D-50) спрашивает модуль пользователей, будущие служебные входы приложения — так же. Вызывающий — `SystemCaller` с `from: { kind: 'app', module: <имя приложения>, name: <имя входа> }` (например `{ kind: 'app', module: 'example-app', name: 'resolveCaller' }`).
- Форма `OperationRef` та же (`module` — имя приложения): лог операций и JSON вызывающего различают такой вызов по `kind`, отдельного типа нет. Имя приложения не совпадает с модулем, поэтому вызов всегда «чужой» (D-43): UC открывает его через `system` в `callers`.

*Почему:* без своего вида вход приложения пишется в лог как UC несуществующего модуля, и след операции вводит в заблуждение. Трек `dmg-core-standalone`.

**D-52. Правила корня сборки и раннера.** Уточняет ARC-07, ARC-08, ARC-09 под D-50.
- **Приложение (ARC-07)** собирает модули, поэтому кроме платформы и контрактов домена импортирует входы (`index`) прикладных пакетов модулей — их фабрики. Внутрь пакета модуля (UC, репозитории напрямую) — нет.
- **Раннер (ARC-08)** импортирует корень сборки, контракты домена и платформу; прикладные пакеты модулей — нет: модули он не собирает, операции вызывает через `ApiApp.dispatch`.
- **Окружение (ARC-09)** читает только точка входа раннера: `process.env` → `AppEnv`. Всё остальное — домен, прикладной слой, приложение, UI — получает его данными.
- **Проверка:** `ArchApp` описывает, кроме модулей, корень сборки и раннеры (каталоги); `arch:check` проверяет их импорты по ARC-04/07/08. Плагин ARC-09 подключается на всё, кроме точек входа раннеров.

*Почему:* после D-50 прежний ARC-07 («только платформа и домен») запрещал бы саму сборку, а корень сборки и раннер не проверялись машинно: ошибку импорта в учебном приложении нашло только ревью. Трек `dmg-core-standalone`.

**D-53. Тип пользователя приложения — в домене.** Уточняет D-04 и D-50.
- Полный тип субъекта (`U` в `Caller<U>`: uuid, роли и т. п.) объявляется в общем домене — `<domain>/shared/` (в учебном примере `example/shared/app-user.ts`, в monorepo — пакет домена). Его импортируют прикладные пакеты модулей, корень сборки и раннеры; домен — только тип, без реализации.
- **Прикладной пакет модуля не импортирует корень сборки и раннеры** (ARC-06): модуль не зависит от приложения, которое его собирает. Проверяет `arch:check` (`AssemblyChecker`).

*Почему:* тип в корне сборки давал зависимость «модуль → приложение → модуль»: в monorepo это цикл пакетов, и каркас `init` повторил бы его. Трек `dmg-core-standalone`.

**D-54. Видимость операции для транспорта — `callers` и Policy; вызов по имени — `dispatchByName`.** Уточняет D-45, D-49 и D-50. Контракт модуля (`contract.ts`, D-45) — граница TS-импортов между модулями; транспорт и раннеры адресуют UC по имени и исполняют любой UC из `ModuleDef.useCases`, кто может вызвать — решают `callers` и Policy. `apiApp.dispatchByName(module, command, caller, trace)` — вход по имени модуля без Def (раннер `call`, будущий HTTP `POST /api/<module>`); `dispatch` по Def — типизированная обёртка над ним. Резолвер каркаса `init` до модуля пользователей — заглушка разработки: uuid из CLI → `UserCaller` без ролей, только канал `cli`, иначе исключение; отступление от D-50 только для каркаса ([project.md](./guides/project.md) §3).

**D-55. Тесты UC/ER/Job — на фейке порта (`MemoryRepo`, `<a>.repo.fake.ts`).** Уточняет D-36 и D-43; пирамида — [testing.md](./testing.md) §3–4.
- **Фейк порта** — `<A>RepoFake` в `<app>/<m>/<a>/<a>.repo.fake.ts` рядом с портом, наследник `MemoryRepo<A, S>` из `dmg-core/testing`. Создаёт `gen aggregate` (и `gen uc`, если фейка нет). Тип снапшота — `StateOf<typeof <A>ArDef>`: DOM-01 исключений для фейка не получает.
- **`MemoryRepo`** — наследник `VersionedRepository`: `save` сверяет версию, как настоящий репозиторий (`VersionConflict`); `seed(...)` — начальные записи, `saved` — записанное через `save` (без `seed`), `restored(uuid)` / `restoredOrThrow(uuid)` — новый Ar из памяти, `failOn(uuid)` — сбой записи.
- **Выборку `find*` фейк не реализует.** Метод порта объявляется `this.unanswered(...)` (вызов без ответа — исключение), ответ тест задаёт присваиванием поля (`tasks.findDone = async () => […]`) — типизированно, без generic по порту и `keyof`. `findById` — через `restored`. Корректность выборки проверяет только контрактный тест репозитория во временном каталоге.
- **Пирамида хранилища:** UC/ER/Job — фейк; репозиторий и smoke модуля — настоящий репозиторий во временном каталоге; e2e UI — настоящие репозитории.
- **TST-07:** рабочий код не импортирует фейки (`*.repo.fake`) и `dmg-core/testing` — их видят только тесты и сами фейки; проверка — lint.

*Почему:* тест UC на JSON во временном каталоге проверял заодно выборку и формат файла, был медленнее и дублировал контрактный тест репозитория; ответ `find*` в тесте делает сценарий UC явным. Фейк лежит рядом с портом, поэтому его переиспользуют тесты UC, ER и Job модуля, а TST-07 не даёт ему попасть в рабочий код. Трек `dmg-cleanup` u7-school.

**D-56. Отсев повторов command UC по `requestId`.** Уточняет D-49 и [transport.md](./reference/transport.md) §2; аналог inbox событий (D-47) для входа транспорта.
- **Где:** `dispatch` модуля (через него идут все входы, D-49/D-54). Отсеивается только command UC со следом `cause.kind: 'request'`, где `requestId` прислал клиент. Query, след события или Job, серверный `requestId` и вызывающий `system` (вызов из другой операции или приложения — его определяет внешняя операция) — без отсева.
- **Ключ:** модуль + вызывающий + `requestId`. Вызывающий: `user` — `subjectId`, `delegate` — `subjectId` и `actorId`, `guest` — канал и `channel.visitorId` из следа (посетитель `42` в разных каналах — разные гости); гость без `visitorId` — без отсева (иначе один гость получит ответ другого).
- **Вход:** канонический JSON `{ uc, input }` (ключи объектов отсортированы) хранится строкой рядом с ответом; другой вход с тем же ключом — конфликт.
- **Хранилище — порт `ReplayStore`** в `AppContext.replay` (рядом с `inbox`): `claim` занимает ключ до исполнения (запись «в работе»), `complete` сохраняет ответ, `release` снимает запись; `complete` и `release` — только с токеном владельца из `claim` (поздний итог после TTL не трогает чужую запись). `claim` атомарен, ответ JSON-совместим и отдаётся копией. Реализация по умолчанию — `InProcReplayStore` (TTL и ёмкость); хранилище, переживающее рестарт, даёт приложение. TTL по умолчанию — 24 ч.
- **Что сохраняется:** только `Ok`. На `Err` запись снимается, повтор исполняется заново: неудавшаяся команда ничего не записала (UoW), а `VERSION_CONFLICT` или `internal` при повторе может пройти. Повтор с тем же входом получает сохранённый `Ok` без исполнения UC (без Policy, без записи в лог операций).
- **Ошибка ядра `REQUEST_CONFLICT`** (`conflict`), payload `{ requestId, reason: 'input' | 'in_progress' }`: `input` — тот же ключ с другим входом, `in_progress` — первый запрос ещё исполняется. Сбой процесса между записью агрегатов и `complete` оставляет запись «в работе» до TTL: повтор получает `in_progress`, а не второе исполнение.
- **Сбой хранилища** наружу не выходит (ERR-07): сбой `claim` — `SERVER_INTERNAL` и `error` в логгер, UC не исполняется; сбой `complete` или `release` — `error` в логгер, результат UC как есть.
- **Серверный `requestId`:** `Trace.fromRequest` без id клиента ставит `cause: { kind: 'request', requestId, generated: true }`; признак идёт в лог операций и `TraceJson`.

*Почему:* `requestId` по D-49 — одно намерение клиента и ключ идемпотентности, но `dispatch` его не исполнял (DEBT-1): повторная доставка (ретрай HTTP, повтор апдейта Telegram после рестарта) исполняла команду дважды. Сохранять только `Ok` проще и безопаснее: ошибка не меняет состояние, её дешевле получить заново. Трек `dmg-cleanup` u7-school.

**D-57. Ожидаемая версия от клиента — поле входа UC; VO `meta` отвергнут.** Уточняет D-36 и D-49.
- **Ожидаемая версия** — версия агрегата, которую видел клиент (оптимистичная блокировка со стороны клиента: кнопка бота устарела, форма открыта давно). UC сверяет её явным шагом `this.expectVersion(ar, input.expectedVersion)` до операции: расходится — `Err(VERSION_CONFLICT)` без фиксации и событий; не прислана — сверки нет. Шаг явный, а не в конвейере: какой агрегат сверять, знает только UC.
- **Канал — поле входа UC** `expectedVersion?: number` (схема — `F.expectedVersion('<агрегата>')`). Сигнатуры `handle`/`execute` не меняются; поле видно в контракте и графе, типизировано по Def; несколько агрегатов — несколько полей; фасады и кнопки бота передают его как обычный вход; оно входит в канонический вход отсева повторов (D-56). `CommandMeta.version` удаляется как неиспользуемое: `meta` команды — только `requestId`.
- **Версия наружу — `ar.version` и поле `version` в `view()`**: state, `view()` и запись по-прежнему одной формы (D-44), метаполя плоские (D-36).
- *Отвергнуто:* `CommandMeta.expectedVersion` (как `If-Match`) — новый параметр во всех UC, одна версия на команду, не видно в контракте, фасады и бот пробрасывают meta отдельно, отсев повторов её не учитывает.
- *Отвергнуто:* VO `meta` (`{ version, createdAt, updatedAt }`) в Ar и `view()` при плоском хранении — state и `view()` расходятся: `readonly` переводит вид в state, на агрегат нужна вторая схема, агрегат со своей формой `V` нельзя передать другому модулю; польза — только группировка полей. Даты к тому же участвуют в доменных решениях (выбор «последнего» по `createdAt`), техническое поле — только `version`. Вынос в `meta` вместе с хранением последователен, но требует миграции данных без выгоды; вернуться к нему можно при миграции дат.

*Почему:* клиент не мог сказать серверу, с какой версией работал, — устаревшее действие проходило молча. Трек `aggregate-meta` u7-school.

**D-58. Шаг `fetch` после Policy: чужие вызовы — после права.** Уточняет D-08, D-40 и D-43.
- **Порядок UC:** `checkCaller` → `parseInput` → `load` → `checkPolicy` → `fetch` → `checkRules` → `execute` → `parseOutput` → фиксация.
- **`load`** загружает контекст Policy — обычно свои агрегаты из репозитория. **`fetch(input, loaded, caller, trace)`** — необязательный шаг (по умолчанию ничего не добывает): вызовы чужих модулей (`this.call`) и всё, что нужно только правилам и операции. Результат `fetch` — объект типа `F` (пятый параметр `UseCaseFromDef`; по умолчанию `unknown`, и `L & F` остаётся `L`); правила и `execute` получают `L & F` одним объектом. Задан `F` без переопределения `fetch` — тип этого не ловит (цена простых типов), ловит тест UC. Ошибка `fetch` возвращается как есть, до UoW: следов нет.
- **Правила — после `fetch`:** контекст правил — ответы зависимостей (`assigneeActive` над ответом `users`). Правило над данными `load` проверяется после чужого вызова — цена порядка; если важно, это право субъекта (Policy) или вопрос Ar.
- **API-07 (lint):** `this.call` в `load` — ошибка. Вызов, ответ которого нужен Policy, остаётся в `load` с подавлением и причиной: `// biome-ignore lint/plugin: <что из ответа нужно Policy>`.
- *Почему не в `load`:* право проверяется до любой работы ради запроса. Иначе не-владелец по коду ошибки зависимости (`USER_NOT_FOUND` вместо `ACCESS_DENIED`) узнаёт о существовании чужой записи (изоляция арендаторов), зависимость получает вызов на каждый запрос, которому всё равно откажут, а её сбой подменяет отказ права (`SERVER_INTERNAL` вместо `ACCESS_DENIED`). При выносе модуля в сервис (D-28) это сетевой вызов. Платформа безопасна по умолчанию, а не дисциплиной каждого UC.
- *Отвергнуто:* порядок без `fetch` и приём «ответ зависимости значением в контекст, отказ — правилом» — повторяется в каждом UC, каждой ошибке зависимости нужна копия в своей группе, отказ доступа зависимости скрывается, проверить размещение нечем. *Отвергнуто:* правила до `fetch` (`load` → Policy → правила → `fetch`) — правило над ответом зависимости стало бы невозможно.

*Почему:* TR-27 трека `dmg-core-extract` u7-school — вызов `users.getUser` в `load` учебного `assignTask` шёл до Policy. Трек `app-assembly` u7-school; первая редакция («`fetch` не вводим») отменена до публикации.

## Документация

**D-59. Документация платформы: четыре типа, ссылки в одну сторону, комментарий — только невыводимое из кода.**
- **Типы и ответственность:**
  - `docs/concepts/` — как устроено и почему: потоки, жизненный цикл, схемы (mermaid). Без перечня полей и правил.
  - `docs/guides/` — как сделать артефакт на учебном модуле.
  - `docs/reference/` — нормативное: правила с ID, имена, стиль TypeScript, коды ошибок. Каждый факт — в одном месте.
  - `decisions.md` — контракт или компромисс и его причина (`D-NN`).
  - JSDoc — контракт юнита, до 6 строк; длиннее — со ссылкой `@see` на документ или тест.
- **Ссылки в одну сторону:** concepts → guides, reference, decisions; guides → правила по ID и concepts; reference → только `D-NN`. Код ссылается на документы через `@see`; документ на код — только на образцы и в `covers:` (пути исходников во front-matter concepts и guides). Ссылки проверяет тест в `check`.
- **Входы:** `docs/index.md` — для человека, `llms.txt` — для агента (reference и guides; concepts — по требованию).
- **Актуальность:** затронутый документ обновляет автор среза в том же срезе, `reviewer` проверяет; какой документ затронут, подсказывают `covers:` и `docs:impact`. Отдельного владельца документов нет — он не знает контекста изменения; расхождения ищет периодический аудит.
- **Комментарий оправдан** (CODE-04), если из кода и типов нельзя вывести: порядок или побочный эффект; причину выбора; единицы и допущения; отклонение от правила с его ID. Не оправданы: пересказ сигнатуры, перечень параметров, ссылки на треки (`TR-NN`), «временная реализация», сценарии сбоев прозой — их место в именованном тесте. Ссылка на решение — одна `D-NN`, в шапке юнита, не в середине фразы. Длинный JSDoc без `@see` — предупреждение в `check`, основная проверка — `reviewer`.

*Почему:* JSDoc на 15–20 строк подменял недостающее объяснение «как устроено», а смешанные документы (`transport`, `errors-result`, `layers`) повторяли один факт в нескольких местах — при изменении правилось одно из них. Трек `dmg-docs` u7-school.

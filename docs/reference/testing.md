# Тестирование

**Назначение:** общие правила тестов. Правила с ID — раздел TST в [rules.md](./rules.md).

---

## 1. Принципы

- **TDD:** тест пишется до кода. Покрытие — сигнал, не цель: пробел показывает непроверенное поведение, порога нет (§5).
- **Изоляция:** тесты не зависят друг от друга и от порядка; состояние — с нуля (`beforeEach` или свежие экземпляры).
- **Размер:** 10–20 строк; подготовку данных — в хелперы. Тест — документация поведения.
- **Группировка:** `describe` по методу/операции, `it` — по ветке поведения.
- **Один тест — одна причина падения.**

## 2. Проверка отказов

Проверяется **конкретная ошибка**, а не факт отказа:

```typescript
const res = task.complete(at);
expect(res.ok).toBe(false);
expect(res.ok ? undefined : res.error.code).toBe('TASK_ALREADY_DONE');
```

Хелперы из `dmg-core/testing`: `expectErr(res, 'TASK_ALREADY_DONE')` возвращает ошибку, суженную по коду; `expectOk(res)` — значение. Не зависят от раннера, при несовпадении бросают.

## 3. Пирамида

| Уровень | Что тестируется | Объём |
|---|---|---|
| **Схемы** | своя логика схемы: `refine`/`transform`, отказ прежних форм записи, схема state, разбираемая при чтении хранилища. Приём и отказ полей фреймворка (`F.uuid`, `picklist`, `variant`, `expectedVersion`) не тестируются — их держат фреймворк и вызывающие | по логике |
| **Ar** | каждая ветка `Ok`/`Err` мутирующих методов, переходы статусов, события; подключение схемы — 1–2 теста | максимальный |
| **Policy** | каждое правило: allowed и denied, роли, свой/чужой, контекст | все правила |
| **DCS / DQS** | сценарии координации и вычисления на готовых агрегатах | все методы |
| **Репозиторий** | контракт: restore/snapshot, поиск, `undefined` при отсутствии; временный каталог | контракт |
| **UC / ER / Job** | цепочки: нет актора → `UNAUTHORIZED`, нет сущности → `*_NOT_FOUND`, политика → `ACCESS_DENIED`, успех → регистрация в UoW и события; каждая собственная ошибка. Порты — фейки (`MemoryRepo`, `StubFacade`) | по ошибкам |
| **Модуль** | smoke: один успешный вызов каждого UC на реальных репозиториях (временный каталог) | по UC |
| **Контрактные** | граф и правила MAN/ARC/ERR — `arch:check` в `check`; состав Def (`errors`, `emits`, `calls`) руками не повторяется. В тестах модуля — один тест состава: список UC и `dependsOn` | автоматически + 1 на модуль |

**Круг через JSON (D-46)** держат тесты фреймворка: `Caller`, `Trace`, команда, конверт события, снапшот Ar и ответ UC (`serializeResult` → `restoreResult`) восстанавливаются из `JSON.parse(JSON.stringify(…))`. В проекте они не повторяются; повтор события с новым `eventId` проверяет тест реакции через `expectIdempotentReaction` (повтор того же `eventId` отсеивает inbox, D-47).

## 4. Моки

- Домен не мокается: он чистый, тесты работают с настоящими агрегатами.
- В прикладном слое мокаются порты (репозитории, фасады) — типизированно, без `any`.
- Время (D-34): домен получает момент аргументом операции (`task.complete(at)`) — в тесте Ar это просто константа. Прикладной слой берёт его из часов приложения (`this.now()` в UC/ER/Job); в тесте — `testAppContext({ at })` и `ctx.setNow(ts)` (`dmg-core/testing`). Глобальных часов нет, `Date` напрямую не читается.
- Пирамида хранилища: UC/ER/Job — фейк порта; репозиторий (контракт, каждая выборка) и smoke модуля — настоящий репозиторий во временном каталоге; e2e UI — настоящие репозитории.
- Фейк порта — `<A>RepoFake` в `<a>/<a>.repo.fake.ts` рядом с портом (создаёт `gen aggregate`): наследник `MemoryRepo` из `dmg-core/testing`. `save` сверяет версию, как настоящий репозиторий (`VersionConflict`); начальные записи — `seed(...)`; записанное — `saved` («ничего не записано» — `saved` пуст); чтение — `restored(uuid)`; сбой записи — `failOn(uuid)`. Тип снапшота — `StateOf<typeof <A>ArDef>` (DOM-01). Выборка `find*` (D-84): тривиальная — через `this.where(s => …)` (предикат по снимку, новые Ar в порядке вставки; `seed` и `save` видны); если тесту нужен заданный им ответ (порядок, сбой, нетривиальный запрос) — метод порта объявлен `this.unanswered(...)`, ответ тест задаёт присваиванием (`tasks.findDone = async () => [...]`). В `where` — только предикат по полям снимка, без сортировки и логики выборки; корректность выборки — контрактный тест настоящего репозитория. Образец — `src/testing/example/backend/todo/task/task.repo.fake.ts`.
- Фикстуры чужого модуля (субъект `Caller` — Ar пользователей) тест не собирает сам: их отдаёт владелец входом `<domain>/<m>/testing.ts` (`userSubject({ uuid, roles })` → `UserAr.restore(...)`). Импортирует его только тестовый код — `*.test.ts`, `*.fixture.ts`, `*.test-kit.ts`, фейки, каталоги `tests/`, сам `testing.ts`; из рабочего — TST-07 в `arch:check` (D-70).
- Готовые `testAppContext` (шина — `RecordingBus`, логгер — `MemoryLogger`), `MemoryBus` (доставляет события подписчикам), `MemoryRepo`, `StubFacade`, `expectIdempotentReaction` — для UC/ER без реального приложения (`src/testing/index.ts`); учебный модуль — `src/testing/example`.
- Мини-монорепо (D-108, D-111) — `Monorepo` из `dmg-core/testing` (типы `FixtureManifest`, `FixtureSection`) для проверок единиц выноса (ARC-14…ARC-16), в том числе своей единицы поставщика: `Monorepo.create()` — проект `proj` (`ArchApp.project`) во временном каталоге; `root(manifest)`, `unit(dir, manifest)` — `package.json` корня и пакетов (зависимость — имя: внешний пакет → `file:`, иначе `workspace:*`, офлайн); `vendor(name, files?, exports?)` — внешний пакет вне проекта, с `exports` — только его подпути; `write(path, ...specs)`, `file(path, text)` — файлы; `install()` — настоящая изолированная установка Bun; `dispose()`. Кэш резолвера Bun живёт весь процесс и не забывает разрешений: сценарий — в своём каталоге, фикстура пишется целиком до `install()` и после не меняется.
- Учебное приложение целиком — вход `dmg-core/testing/example` (D-101): `ExampleApp`, `ExampleAppDef`, типы `ExampleAppEnv`, `ExampleAppPorts`, `ExampleUser` и контракты модулей todo и users; контракт todo отдаёт и Ar, Policy, правила задач и `OPEN_TASKS_LIMIT` (D-104). Им пользуются тесты внешних пакетов (поставщики графа, UI). Стабилен только этот вход; глубокие пути `dmg-core/testing/example/*` работают, но могут меняться вместе с раскладкой примера. В `dmg-core/testing` приложения нет: сборка и контракты не попадают во все тесты.
- Данные теста (D-84): след запроса — `TEST_TRACE` (`requestId: 'r-1'`) или `testTrace()` — свежий `r-<n>` на каждый вызов (отсев повторов D-56 считает одинаковый `requestId` повтором; вместо `crypto.randomUUID()`), `testTrace('r-42')` — заданный; uuid — `testUuid(n, prefix?)` → `<prefix>-0000-4000-8000-<n, 12 hex>`, проходит `F.uuid`; временный каталог — `TempDir.create(prefix?)` (`path`, `file(...segments)`, `dispose()`, `using`) или `useTempDir(prefix?)` — свой каталог на каждый тест блока (`beforeEach`/`afterEach`, возвращает `() => TempDir`) вместо ручного `mkdtemp`/`rm`.

- Персональные данные (D-86): механика маскирования проверена в пакете; модулю достаточно теста, что помеченные поля state и схем операций — `F.sensitive`, и сквозного прогона, что значения нет в строке лога ([oplog.md](./oplog.md)).

## 5. Польза на тест (TST-08)

Набор тестов минимален при полном покрытии поведения: каждый тест защищает то, чего не защищает другой. Число тестов и покрытие — сигналы, не цели; порога нет. Рост числа без нового поведения — повод искать дубль, убыль при том же поведении — норма. Рефакторинг не меняет функционал — число тестов не должно расти так, будто он добавлен.

- **Тесты затронутого модуля пересматриваются целиком** — при рефакторинге, переносе и пересмотре решения: не только изменённые файлы и не только diff, но и соседние тесты модуля. Затронутый модуль — модуль, код или тесты которого меняет задача; в срезе — модуль среза. Каждому — вопрос §5.1; ответ — оставить, переписать (имя шире проверки, проверка слабее заявленной) или удалить.
- **Логика переезжает** (сборка ответа из UC в DQS, правило в Ar или Policy, legacy → Def) — её сценарии **переезжают**, а не копируются: у вызывающего они удаляются в том же шаге. У вызывающего остаётся своя ответственность: для UC — загрузка, вызов Policy, ошибки, `callers`, вход, запись в UoW; плюс один сквозной сценарий, что вызов доходит до нижнего уровня.
- **Решение пересмотрено** (поведение отменено или заменено) — тест отменённого поведения удаляется или переписывается под новое. Под зелёное его не подгоняют: убранная ветка, «что-то упало» вместо конкретной ошибки, `skip` — потеря защиты, а не пересмотр.
- **Дубль удаляется сразу**, в том же шаге, без записи в долг: отложенная чистка копится — ревью видит изменения одного шага, а повторы складываются из нескольких.
- **Не теряется поведение, а не тест.** Каждое удаление или слияние — строкой «что защищал → где покрыто / почему не нужно»: «где покрыто» — файл и `it`, который уронит та же ошибка; «почему не нужно» — причина из §5.1 (фреймворк, фейк, тавтология, мёртвый код) или отменённое поведение. Ревьюер сверяет; удаление без строки не принимается.
- **Один сценарий — один файл:** новый файл «на новое поле» или «после переезда» не заводится рядом со старым — сценарии дописываются в существующий, старый файл удаляется.

Признаки лишнего теста (кандидат на удаление; поведение фреймворка, фейки и тавтологии — §5.1, тесты типов — §5.2):

- правило проверено уровнем ниже и повторено выше: `it` UC проверяет не свою ответственность (загрузка, вызов Policy, ошибки, `callers`, вход, запись в UoW), а правило вызываемого; экран или сторис повторяет резолвер;
- общий помощник проверен в каждом вызывающем: одинаковое тело `it` в нескольких файлах;
- сквозной или приёмочный сценарий дословно повторяет тест нижнего уровня: те же имена, фикстура, ожидаемые строки;
- транзит по слоям: значение, которое слой не меняет (описание поля, текст отказа, подсказка), проверено на каждом слое, через который проходит. Остаются тест владельца преобразования и один сквозной; признак — один литерал в ожидании в нескольких файлах разных слоёв;
- копия соседнего теста без нового класса входа: `it.each` по параметру, который код не читает, по `it` на шаг одного обработчика, строка таблицы конфигурации отдельным `it`;
- тест Def в домене и тест того же UC в прикладном слое повторяют приём и отказ одних и тех же полей: пайплайн разбирает вход и выход схемами Def на каждом вызове. Своя логика схемы (`refine`/`transform`) проверяется один раз — на уровне «Схемы» (§3);
- тест-некролог: проверяет, что удалённых имён и кодов больше нет (`not.toHaveProperty`, `not.toContain` по старым кодам) — ничего из нынешнего поведения он не защищает;
- имя шире проверки: заявлены две ветки, проверяется одна — переписать, а не удалять.

## 5.1 Тест проверяет код модуля (TST-09)

Вопрос к тесту: какая ошибка в коде модуля уронит его, и только его? Нет такой — тест не пишется. Не тестируются:

- поведение фреймворка: разбор схем, `UNAUTHORIZED` без субъекта, `VersionConflict`, «событий нет» у операции, которая их не поднимает;
- фейк, стаб или фикстура: фильтр выборки, который делает фейк, — контракт репозитория;
- тавтология: константа против той же константы, ожидание, посчитанное тем же рабочим кодом, однострочный геттер, пустой вход на `filter`/`map`;
- вопрос Ar с единственным потребителем, покрытым тестом, — проверяется через потребителя;
- тексты `label` ошибок — видимые пользователю тексты проверяют тесты UI.

Тест мёртвого экспорта — сигнал удалить код, а не только тест.

## 5.2 Тесты типов (TST-10)

Тест типа проверяет вывод или запрет на уровне `tsc`. Рабочий код, который пользуется типом, тоже проверяется `tsc` в `check`; запрещённое он не пишет.

- **Позитивный** (`expectTypeOf(x).toEqualTypeOf<…>`, `Equal<…>`) не пишется, если тот же вывод использует рабочий код или учебный модуль (`src/testing/example/`). Остаётся только на неочевидный вариант, которым рабочий код не пользуется, но который тип гарантирует.
- **Негативный** `@ts-expect-error` — на публичную гарантию фреймворка: вызов Def вне `calls`, ошибка вне Meta, мутация `ReadonlyAr`/`state`, команда чужого модуля. Если тип расширится до `string`/`any`, упадёт только он. Одна гарантия — один негативный тест.
- **`@ts-expect-error`** — с пояснением и ровно одной ожидаемой ошибкой в строке: голый маркер проходит на любой ошибке компиляции.
- **`@ts-expect-error` ради рантайм-ветки** (неизвестная команда, `as never`) — не тест типа: оценивается как обычный тест (§5, §5.1).

## 6. Защита от регресса и чистота правок

**Критично:** реализация, исправление или рефакторинг не приводят к регрессу функционала вне задачи.

- **Запрещено** менять функции и тесты вне области задачи; для тестов область — затронутый модуль целиком (§5).
- **Исключение:** если правка соседнего кода необходима (критическая ошибка или требование задачи) — сообщить владельцу задачи и получить явное разрешение. Агент-исполнитель в этой ситуации останавливается и возвращает эскалацию.

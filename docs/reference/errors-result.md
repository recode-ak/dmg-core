# Ошибки и Result

**Назначение:** правила отказов — `Result`, модель ошибки, базовые ошибки ядра, гарантии исполнения UC. `Result` (`ok`/`err`), `ErrorDef`, `CoreErrors` и UoW — в `dmg-core`. Представление ошибок в транспорте — [transport.md](./transport.md). Решения — D-13, D-15, D-36, D-49 ([decisions.md](../decisions.md)).

---

## 1. Ключевые правила

1. Штатный бизнес-отказ («задача уже выполнена», «нет прав», «не найдена») — **значение** `Err`, а не исключение.
2. `throw` допустим только для: бага, нарушения инварианта (данные повреждены), системного сбоя (диск, сеть).
3. Мутирующие методы Ar, DCS, фасады и UC возвращают `Result<T, E>`; `E` — union объявленных ошибок. Методы-вопросы и DQS `Result` не возвращают.
4. UC может вернуть **только** ошибки из своего `errors` плюс базовые ядра — проверяет компилятор.
5. Вызывающий код (story, ER, UC) обрабатывает `Err` явно: `switch` по `code` с веткой по умолчанию.
6. Нарушение, которое в production не должно ронять операцию пользователя (расхождение реализации с контрактом, подозрительное, но не опасное состояние), не бросается и не проглатывается молча: в test и development — исключение, в production — как минимум `logger.warn` с источником (ERR-07). Пример — сверка `emits`/`touches`/`calls` в UoW и резолвере.

## 2. Модель ошибки

`code` + `kind` + `label` + `description` + `payload`. **Ошибка не знает транспорт.**

| kind | Смысл | Примеры |
|---|---|---|
| `validation` | вход не прошёл схему | `INPUT_VALIDATION` |
| `unauthorized` | `kind` вызывающего не входит в `callers` UC | `UNAUTHORIZED` |
| `access` | политика отказала (+ правило и `denyMessage`) | `ACCESS_DENIED` |
| `not_found` | сущности или операции нет | `TASK_NOT_FOUND`, `OPERATION_NOT_FOUND` |
| `conflict` | состояние не допускает операцию | `TASK_ALREADY_DONE` |
| `internal` | сбой, баг, невалидный выход | `SERVER_INTERNAL`, `OUTPUT_VALIDATION` |

- Коды — UPPER_SNAKE с префиксом сущности, **уникальны в приложении** (контрактный тест).
- Агрегат объявляет ошибки группой `ErrorDef.define`; UC и фасад **ссылаются** на них, результат Ar возвращается как есть.
- Ошибки зависимостей — по ссылке через контракт фасада; перевод — только при смене смысла.
- **Сериализация:** в ответе транспорта только `code`, `kind`, `payload` (`ErrorDef.serialize`); тексты клиент восстанавливает по Def (`ErrorDef.restore`, `UseCaseDef.restoreResult`). Код или payload вне контракта UC восстанавливаются как `SERVER_INTERNAL`, о расхождении сообщает клиент транспорта (`moduleApi`).

**Базовые ошибки ядра** (`CoreErrors`) подмешиваются в каждый UC:

| Код | kind | Когда | payload |
|---|---|---|---|
| `UNAUTHORIZED` | `unauthorized` | вид вызывающего не в `callers` | `{ callerKind }` |
| `INPUT_VALIDATION` | `validation` | вход не прошёл схему UC | замечания схемы |
| `ACCESS_DENIED` | `access` | Policy отказала | `{ rule, denyMessage }` |
| `OUTPUT_VALIDATION` | `internal` | выход UC не прошёл схему | замечания схемы |
| `VERSION_CONFLICT` | `conflict` | версия агрегата в хранилище или ожидаемая версия клиента расходится с текущей (D-36, D-57) | `{ aggregate, uuid }` |
| `OPERATION_NOT_FOUND` | `not_found` | по адресу нет модуля или UC с именем из команды (D-49) | `{ module, uc }` |
| `REQUEST_CONFLICT` | `conflict` | повтор command UC с тем же `requestId` клиента (D-56, [transport.md](./transport.md) §2) | `{ requestId, reason: 'input' \| 'in_progress' }` |
| `SERVER_INTERNAL` | `internal` | непредвиденное исключение, ошибка вне контракта | нет |

## 3. Исполнение UC (`handle`)

Порядок шагов — `protected` методы `UseCaseFromDef`: право вызова (`callers`) → валидация входа → `load` → Policy → `fetch` (D-58) → доменные правила (`rules`) → `execute` → валидация выхода → при `Ok`: `uow.commit()` → публикация событий записанных агрегатов → запись в лог операций (при любом исходе, D-43).

- `callers` проверяется до чтения данных; Policy — после `load`: отказ «не найдено» своего агрегата возможен раньше `ACCESS_DENIED`. Если существование записи само секретно, правило без контекста выносится в проверку до `load`.
- Чужие модули вызываются только в `fetch`, после Policy (API-07).
- Невалидный выход — `OUTPUT_VALIDATION`: ничего не сохраняется и не публикуется.
- Непредвиденное исключение ловится, логируется и превращается в `SERVER_INTERNAL`.
- События публикуются **только у записанных агрегатов**. Сбой записи N-го агрегата (`VERSION_CONFLICT` или исключение) не откатывает записанные до него (D-15): их события публикуются, события N-го и следующих — нет.
- Репозиторий сверяет версию агрегата (база `VersionedRepository`) и бросает `VersionConflict`; UoW возвращает `VERSION_CONFLICT`. Новый агрегат при занятом uuid — тоже конфликт.
- Пока UoW сохраняет без отката (D-15), UC по возможности меняет один агрегат; согласованность между модулями — через события.
- ER возвращает `Result`; сбой реакции логируется и попадает в журнал сбоев.

## 4. Тестирование

- Проверяется конкретный `code` (и при необходимости `kind`), а не факт ошибки.
- Ar: тест на каждую ветку `Ok`/`Err` каждого мутирующего метода.
- UC: тест на каждую собственную объявленную ошибку.
- Ядро: тесты `handle()` на перехват исключений, порядок commit → publish, валидацию выхода до фиксации.

# Слои и пакеты

**Назначение:** оси приложения на DMG, кто кого импортирует, доменный API, доступ к entity, обязанности реализаций и раннеров. Файловая структура и имена — [naming.md](./naming.md); куда поместить доменную логику — [domain-modeling.md](./domain-modeling.md). Раскладку проекта по каталогам задаёт секция `gen` его `.dmg/config.json` (`GenLayout`); каталоги слоёв поставщиков — секция `layers` того же файла (`GenLayout.layerDirs()`, `guides/provider-extension.md`). Решения — D-05…D-07, D-15, D-33, D-39, D-42, D-43, D-45, D-49, D-50, D-52, D-106…D-108, D-110, D-111 ([decisions.md](../decisions.md)).

---

## 1. Оси

| Ось | Где | Роль |
|---|---|---|
| **Фреймворк** | `dmg-core`, поставщики графа (пакеты npm) | `Result`, Def-классы, базовые классы исполнения, `F.*`, UoW, граф-движок, проверки |
| **Платформа приложения** | `kernel` приложения (`platform/kernel`), домен (`platform/domain/<m>`) | едина при любом способе запуска; из неё строится граф. `kernel` — простой тип субъекта и роли, общие поля и VO, чистые помощники; домен — предметная область и все контракты |
| **Реализации** | пакет реализации модуля (`backend/<m>`); необязательно — общее реализаций (`backend/app`) | прикладной слой: UC/ER/Job, репозитории, фабрика модуля. **1:1 с модулем домена**. `backend/app` — базовые классы и замыкания дженериков исполнения над доменом |
| **Раннеры** | сборка (`runners/assembly`), раннеры-процессы (`runners/<r>`) | сборка — корень сборки: контекст, хранилища, модули, резолвер `Caller`; раннеры-процессы — точки входа, транспорты (cli, http, mcp), UI |

Зависимости: раннеры → реализации → `backend/app` → домен → `kernel` → фреймворк (D-106). Пути — от корня исходников: в `single` — под `src/`, в `monorepo` каждый каталог оси — пакет `workspaces` со своим `src/`, у домена — один пакет `platform/domain`, модули — `src/<m>` (`platform/kernel` → `@<scope>/kernel`, `backend/<m>` → `@<scope>/be-<m>`, [naming.md](./naming.md) §1). Каталоги задаёт секция `gen` (`GenLayout`), раннеры-процессы — `ArchApp.runners`.

## 2. Импорты

| Слой (имя в `arch:check`) | Видит | Нарушение |
|---|---|---|
| `kernel` | корень `dmg-core`, valibot | ARC-02 |
| домен (`domain`) | `kernel`, корень `dmg-core` (не `/app`, `/graph`, `/arch`), valibot; чужой модуль — `contract` и только из `dependsOn` | ARC-02, ARC-04 |
| общее реализаций (`backend-app`) | `kernel`, контракты домена, `dmg-core/app` | ARC-06 |
| пакет реализации модуля (`backend`) | `kernel`, `backend/app`, свой модуль домена — `index` и `contract`, чужой — `contract` и только из `dependsOn`, `dmg-core/app`; другие реализации — только фасады через `deps` | ARC-06, ARC-04 |
| сборка (`assembly`) | `kernel`, контракты домена, `backend/app`, входы (`index`) пакетов реализации — для фабрик модулей, фреймворк | ARC-07 |
| раннер-процесс (`runner`) | сборку, `kernel`, контракты домена, фреймворк; UC — только через `api.dispatch` | ARC-08 |

- Видимость — белый список: импорт в слой, которого нет в строке, — нарушение с ID слоя-импортёра. Импорт внутри своего слоя и своего модуля свободен; раннеры-процессы — один слой, импорт между ними не ограничен слоями (в `monorepo` границу пакетов держат ARC-14, ARC-15). Файл принадлежит слою с самым глубоким каталогом (D-107).
- Файл вне всех слоёв (скрипты, вход графа) видит модуль домена только через `contract` (ARC-04), остальное — свободно (вход графа — ещё ARC-16 в обеих формах: его замыкание по локальным импортам не доходит до реализаций, D-111); импорт из слоя в файл проекта вне слоёв — нарушение с ID слоя-импортёра.
- Рабочий код не видит тестового: вход `testing` модуля домена, фейки, `dmg-core/testing` (TST-07). Тестовый код видит `testing` модуля домена там же, где его `contract` (D-70).
- Пакеты npm слои не проверяют: подпути `dmg-core` и valibot для платформы приложения — линтер (ARC-02); объявлены ли пакеты — ARC-14.
- Слой поставщика графа объявляет видимость тем же типом; со слоями реализаций фреймворка (`backend`, `backend-app`) он не связан ни в `sees`, ни в `seenBy` (ARC-13, D-107). Слой поставщика бывает по модулям — `AppDef` или своим (`perModule`, D-110): каталоги — шаблоны с `{m}`, вход модуля для чужого кода — `entry` слоя (без него — `ArchApp.entry`), какие чужие модули видны — `others` доступа, чужой модуль своего слоя — ссылкой слоя на себя в `sees`.
- Подкаталог на месте `{m}` шаблона слоя по модулям (домен, `backend`, слой поставщика), имя которого не модуль слоя и в котором нет каталога другого слоя, — ARC-13 (D-111): `backend/app` и каталог слоя не по модулям рядом с шаблоном — не нарушение.
- Отступление от доступа слоя поставщика — только если доступ его разрешает (`debt: true` со своим `rule`): запись реестра долга кода с полем «Правило» снимает нарушение в файлах своего Места; реестр — `ArchApp.debt` (ARC-12, D-111). Правила слоёв фреймворка отступлений не допускают.
- Проект без каталогов фреймворка — `ArchApp` без `layout` (домен — пакет): проверяются раннеры, слои поставщиков и единицы; мест `kernel`, домена, реализаций и сборки нет, файлы модулей не проверяются (D-111).
- Подпути `dmg-core`: корень — ядро и Def-классы; `/app` — исполнение (UC/ER/Job, модуль, UoW, шина); `/graph` — граф; `/arch` — проверки; `/testing` — помощники тестов.
- Граф `dependsOn` — DAG: подписчик зависит от публикатора, не наоборот. Нижестоящий модуль вышестоящий не вызывает: нижестоящий публикует событие, вышестоящий подписывается ER.

## 3. Доменный API

Любой слой пользуется доменом через API, а не через данные.

1. **Aggregate (Ar)** — бизнес-операции (всегда `Result`), методы-вопросы (никогда `Result`), идентификаторы, события. Не создаёт и не возвращает другой Ar.
2. **Policy** — декларативные права субъекта (`Rule.of`, `Rule.anyOf`, `Rule.allOf`, `Rule.hasRole`, `allowAll`), решение `allowed | denied(rule, message)`.
   **Доменные правила** — декларативные проверки «допустимо ли действие при текущих состояниях агрегатов» без субъекта; `Result` с ошибкой своей группы (D-40).
3. **DCS** (`DomainCommandService`) — операция над несколькими агрегатами или решение, которое не принадлежит одному Ar. Мутирует, возвращает `Result`.
4. **DQS** (`DomainQueryService`) — вычисления на чтение поверх агрегатов. Не мутирует, не зависит от транспорта.

- DCS и DQS могут принимать `Loader<T> = () => Promise<T>` — только для условной или дорогой загрузки; по умолчанию получают готовые агрегаты.
- **`ReadonlyAr<T>`** — тип Ar без мутирующих методов (выводится по возврату `Result`). Его получают фасады, транспорт, UI.

## 4. Доступ к entity

| Кто | Решение (ветвление по полям) | Форма (схема) | Показ (чтение полей) |
|---|---|---|---|
| Ar | да — своё состояние | да | — |
| Def контрактов своего модуля (UC, события, DQS, фасад) | — | да: `v.pick`/`v.omit` из state | — |
| Рендереры UI | нет — методы `ReadonlyAr` | да | да, в т.ч. для реактивности |
| Story, экраны, презентеры | методы `ReadonlyAr`/DQS или поля готового ответа UC (D-72) | нет | передают рендереру |
| DQS | только для показа; условие команды, Policy или правила — метод-вопрос `ReadonlyAr` (D-60) | да: типы и схемы state | да, через `view()` |
| Репозиторий | нет | `restore`/`snapshot` | только ключи хранения |
| Остальные (UC, ER, Job, Policy, доменные правила, DCS, фасады) | нет — методы `ReadonlyAr` | нет | нет |
| Другие модули | нет — `ReadonlyAr` через фасад | нет | нет |

- Контракты (input/output UC, payload событий) — объявленные схемы, выведенные из state, а не сам state.
- Output «получить агрегат» = снапшот, который клиент восстанавливает в `ReadonlyAr`: решения — его методами, поля — рендереру.
- Output «готовый ответ» (D-72) — plain-объект под сценарий UI: признаки и расчёты уже посчитаны доменом на бэке, клиент читает их поля и по ним ветвится. Какой из двух выходов — решается для сценария.
- Тесты строят агрегат через `create`/`restore`.

## 5. Реализации

- **UC** — техническая оркестрация: загрузить Ar → Policy → Ar/DCS → `uow.register(...)`. Сохранение и публикацию событий делает базовый класс после `Ok`.
- **ER / Job** — то же: реагируют, загружают, вызывают домен, регистрируют в UoW.
- **Репозиторий** — порт объявляется в пакете реализации модуля, принимает и возвращает Ar; только хранение. База `VersionedRepository`: `save` сверяет версию (`VersionConflict`), чтение-сверка-запись атомарны под замком `Lock`; наследник реализует `stored(uuid)` и `write(ar)`.
- **Фасад** — рантайм-граница модуля без манифеста: тип `Facade<M>` (`handle` UC модуля с `'system'` в `callers`), реализация `ModuleFacade<M>` в `dmg-core/app` — сахар над командой `ModuleFromDef.dispatch`. Свои типы и методы-обёртки модуль не заводит; выход — как у UC (`Result`), `ReadonlyAr` строит вызывающий.

## 6. Раннеры

- **Сборка** (`runners/assembly`, корень сборки) — класс приложения по `AppEnv` строит `AppContext`, хранилища, модули (через `ApiApp`, раскладка фасадов по `dependsOn`) и резолвер `Caller`. Сервис из одного модуля объявляет свою сборку (D-106).
- **Раннер-процесс** — точка входа: `process.env` → `AppEnv`, транспорт, `Trace`, запуск и остановка; модули он не собирает.
- **Story** — сценарий UI для любого UI-транспорта; вызывает UC через модуль, решает вопросами Ar/DQS или по признакам готового ответа UC, но не по полям state/`view()` (D-72, DOM-18).
- **Презентеры/рендереры** — специфика конкретного транспорта (бот, web): форматирование, компоненты.
- **http / mcp** — предусмотрены генерируемыми из манифестов ([transport.md](./transport.md)); в пакете их нет. **cli** каркаса вызывает UC по имени (`call`, D-54).
- `process.env` / глобальный `config` читает только точка входа раннера (ARC-09): остальные слои получают окружение данными — `AppEnv` и резолвер сборки.

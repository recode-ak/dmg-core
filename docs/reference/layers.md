# Слои и пакеты

**Назначение:** оси приложения на DMG, кто кого импортирует, доменный API, доступ к entity, обязанности прикладного слоя и адаптеров. Файловая структура и имена — [naming.md](./naming.md); куда поместить доменную логику — [domain-modeling.md](./domain-modeling.md). Раскладку проекта по каталогам задаёт секция `gen` его `dmg-core.json` (`GenLayout`). Решения — D-02, D-05…D-07, D-15, D-33, D-39, D-42, D-43, D-45, D-49, D-50, D-52 ([decisions.md](../decisions.md)).

---

## 1. Оси

| Ось | Где | Роль |
|---|---|---|
| **Платформа** | `dmg-core`, пакет приложения (`app`) | фреймворк (`Result`, Def-классы, базовые классы, `F.*`, UoW, граф-движок) и замыкание дженериков приложения (пользователь, резолверы, сборка модулей) |
| **Домен** | пакет домена (`<domain>/<m>`) | чистая предметная область и все контракты |
| **Прикладной слой** | прикладной пакет модуля | реализации UC/ER/Job, репозитории, фасады, сборка модуля. **1:1 с модулем домена** |
| **Входные адаптеры** | приложения (UI, транспорты) | UI (бот, web) и транспорты (http, mcp, cli) |

## 2. Импорты

| Что | Может импортировать |
|---|---|
| `dmg-core` (подпути) | корень — ядро и Def-классы (для домена); `/app` — исполнение (UC/ER/Job, модуль, UoW, шина); `/graph` — граф; `/arch` — проверки; `/testing` — хелперы тестов |
| домен | корень `dmg-core` (не `/app`, `/graph`, `/arch`) и valibot |
| пакет приложения | `dmg-core`, домен |
| прикладной пакет модуля | `dmg-core`, домен, пакет приложения. Другие прикладные пакеты — **нет** (только фасады через `deps`) |
| входные адаптеры | `dmg-core`, домен, пакет приложения; UC вызывают через приложение — `api.dispatch` (ARC-08), пользуются доменным API |

- Чужой модуль импортируется **только** через его `contract.ts` — из домена, прикладного слоя, адаптеров и скриптов; внутри домена — ещё и **только** если тот в `dependsOn`. `index.ts` модуля — для его прикладного пакета.
- Граф `dependsOn` — DAG: подписчик зависит от публикатора, не наоборот. Нижестоящий модуль вышестоящий не вызывает: нижестоящий публикует событие, вышестоящий подписывается ER.

## 3. Доменный API

Любой слой пользуется доменом через API, а не через данные.

1. **Aggregate (Ar)** — бизнес-операции (всегда `Result`), методы-вопросы (никогда `Result`), идентификаторы, события. Не создаёт и не возвращает другой Ar.
2. **Policy** — декларативные права субъекта (`Rule.of`, `Rule.anyOf`, `Rule.allOf`, `Rule.hasRole`, `allowAll`), решение `allowed | denied(rule, message)`.
   **Доменные правила** — декларативные проверки «допустимо ли действие при текущих состояниях агрегатов» без субъекта; `Result` с ошибкой своей группы (D-40).
3. **DCS** (`DomainCommandService`) — операция над несколькими агрегатами или решение, которое не принадлежит одному Ar. Мутирует, возвращает `Result`.
4. **DQS** (`DomainQueryService`) — вычисления на чтение поверх агрегатов. Не мутирует, не зависит от транспорта.

- DCS и DQS могут принимать `Loader<T> = () => Promise<T>` — только для условной или дорогой загрузки; по умолчанию получают готовые агрегаты.
- **`ReadonlyAr<T>`** — тип Ar без мутирующих методов (выводится по возврату `Result`). Его получают фасады, транспорт, UI.

## 4. Доступ к entity

| Кто | Решение (ветвление по полям) | Форма (схема) | Показ (чтение полей) |
|---|---|---|---|
| Ar | да — своё состояние | да | — |
| Def контрактов своего модуля (UC, события, DQS, фасад) | — | да: `v.pick`/`v.omit` из state | — |
| Рендереры UI | нет — методы `ReadonlyAr` | да | да, в т.ч. для реактивности |
| Репозиторий | нет | `restore`/`snapshot` | только ключи хранения |
| Остальные (UC, ER, Job, Story, Policy, доменные правила, DCS, DQS, фасады) | нет — методы `ReadonlyAr` | нет | нет |
| Другие модули | нет — `ReadonlyAr` через фасад | нет | нет |

- Контракты (input/output UC, payload событий) — объявленные схемы, выведенные из state, а не сам state.
- Output «получить агрегат» = снапшот, который клиент восстанавливает в `ReadonlyAr`: решения — его методами, поля — рендереру.
- Тесты строят агрегат через `create`/`restore`.

## 5. Прикладной слой

- **UC** — техническая оркестрация: загрузить Ar → Policy → Ar/DCS → `uow.register(...)`. Сохранение и публикацию событий делает базовый класс после `Ok`.
- **ER / Job** — то же: реагируют, загружают, вызывают домен, регистрируют в UoW.
- **Репозиторий** — порт объявляется в прикладном пакете модуля, принимает и возвращает Ar; только хранение. База `VersionedRepository`: `save` сверяет версию (`VersionConflict`), чтение-сверка-запись атомарны под замком `Lock`; наследник реализует `stored(uuid)` и `write(ar)`.
- **Фасад** — рантайм-граница модуля без манифеста: тип `Facade<M>` (`handle` UC модуля с `'system'` в `callers`), реализация `ModuleFacade<M>` в `dmg-core/app` — сахар над командой `ModuleFromDef.dispatch`. Свои типы и методы-обёртки модуль не заводит; выход — как у UC (`Result`), `ReadonlyAr` строит вызывающий.

## 6. Входные адаптеры

- **Корень сборки** — пакет приложения: класс приложения по `AppEnv` строит `AppContext`, модули (через `ApiApp`, раскладка фасадов по `dependsOn`) и резолвер `Caller`.
- **Раннер** — точка входа: `process.env` → `AppEnv`, транспорт, `Trace`, запуск и остановка; модули он не собирает.
- **Story** — сценарий UI для любого UI-транспорта; вызывает UC через модуль, пользуется Ar/DQS.
- **Презентеры/рендереры** — специфика конкретного транспорта (бот, web): форматирование, компоненты.
- **http / mcp / cli** — генерируются из манифестов ([transport.md](./transport.md)).
- `process.env` / глобальный `config` читает только точка входа раннера (ARC-09): остальные слои получают окружение данными — `AppEnv` и резолвер приложения.

# Делегирование — гайд

**Назначение:** что завести в приложении, если решили, что один человек может действовать от имени другого на срок с отзывом. Фреймворк даёт край: проверку заявки (`DelegationCheck`, `dmg-core/app`), сужения в Def UC и след обоих в логе операций (D-89); записи делегирований, их выдача и отзыв — модуль приложения.

---

## 1. Когда применять

- **Доверие между людьми:** A разрешает B действовать за себя — ассистент, заместитель на время отпуска, родитель за ребёнка. Срок — недели, `readOnly` — по договорённости.
- **Служебный доступ:** поддержка смотрит глазами пользователя, чтобы разобрать обращение. Причина в записи обязательна, срок — часы, `readOnly: true`.
- Не применять для ролей и прав: «кто что может» — Policy по субъекту ([policy.md](./policy.md)). Заместитель — тот же субъект, что замещаемый; правила доступа по каналу не ветвятся (MAN-11).

## 2. Что завести в приложении

1. **Агрегат делегирования** в модуле пользователей: замещаемый, заместитель, конец срока, отзыв, «только чтение» — то, что читает фреймворк (`DelegationRecord`), — и сверх того **кто выдал, причина, когда создано**: фреймворк их не читает, расследованию они нужны.
2. **UC выдачи и отзыва** с `personal: true`; выдачу самому себе (`principalId === actorId`) отвергает доменное правило.
3. **Реализация порта** `DelegationStore.find(delegationId)` — репозиторий агрегата отдаёт `DelegationRecord`; `expiresAt` — число (`Timestamp`), иначе проверка отказывает `expired`.
4. **Заявка в токене или сессии** — `DelegationClaim` (замещаемый, заместитель, делегирование): её достаёт транспорт и передаёт резолверу вместе с личностью.
5. **Экраны:** выдать, посмотреть активные, отозвать; замещаемому — уведомление о выдаче и о действиях заместителя (по логу или событиям).

Агрегата делегирования в пакете нет: правила выдачи (кто кому, на сколько, с подтверждением ли) — предметная область приложения.

## 4. Какие UC пометить `personal`

Действие, которое меняет само доверие или необратимо от имени человека:

- управление делегированием — выдача, продление, отзыв (иначе заместитель продлит себе срок);
- привязка и отвязка канала входа (телефон, Telegram, почта), смена пароля;
- удаление аккаунта;
- платежи и подписки.

`personal` по умолчанию `false`: забытый признак открывает UC заместителю — решается на ревью Def ([use-case.md](./use-case.md)).

## 5. Чеклист правил

- MAN-11 — `callers` без `delegate`: заместитель проходит там, где `user`; Policy и домен видят замещаемого.
- MAN-14 — query вызывает только query: иначе «только чтение» обходится вложенной командой.
- ERR-01 — сбой порта или `getUser` — исключение, не гость и не отказ.
- MAN-05 — вложенный вызов несёт исходного человека (`SystemCaller` с `person()`): `personal` и `readOnly` проверяются на каждом UC цепочки.

## 6. Типичные ловушки

- `readOnly` из заявки → подделывается клиентом. Только из проверенной записи.
- Отказ проверки → `UserCaller` «как сам себе» → заместитель действует от своего имени, не зная этого. Резолвер возвращает `Result`, раннер показывает отказ.
- Запись из query UC: «только чтение» запрещает command UC, а не запись в query — query UC с побочным эффектом обходит признак (долг пакета, DEBT-2).
- Проверка заявки один раз при входе в сессию → отзыв действует только после выхода. Проверка — на каждом запросе.
- Поиск действий заместителя по `--subject` → находит замещаемого. Заместитель — `dmg-core oplog --actor <id>` ([oplog.md](../reference/oplog.md)).

## 7. Как тестировать

- Резолвер приложения: успех, отказ проверки как есть, чужой заместитель, нет пользователя, `readOnly` из записи — образец [example-delegation.test.ts](../../src/testing/example/runners/assembly/example-delegation.test.ts). Причины `DelegationCheck` не повторять — их держит тест пакета.
- UC с `personal` — один тест отказа заместителю на модуль, не на каждый UC: проверку делает фреймворк (TST-09).

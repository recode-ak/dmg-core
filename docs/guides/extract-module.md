# Вынести модуль в сервис — гайд

**Назначение:** как пакет реализации модуля `backend/<m>` (`@<scope>/be-<m>`) уходит из монолита в отдельный процесс или репозиторий (GR-01) и как реализация модуля пишется на другом языке (GR-02): что уже держит проверка структуры и что пишется руками.

> **Вживую не проверено** (D-109). Сценарии обеспечены решениями и раскладкой, машина проверяет только структуру. Ни одного модуля пакетом ещё не выносили: шаги ниже — план, а не пройденный путь. При первом выносе пакет правится по его итогам, статус сценария — [concepts/layers.md](../concepts/layers.md#сценарии-роста).

---

## 1. Когда применять

- Модулю нужен свой процесс или сервер: своя нагрузка, свой цикл выпуска, своя команда (GR-01).
- Реализацию модуля пишут на другом языке по тем же манифестам (GR-02) — §5.
- Профиль — `monorepo`: единица выноса — пакет `workspaces`. В `single` проверки единиц молчат — сначала переезд в `monorepo` ([project.md](./project.md) §1), генератора для него нет.
- Не для разделения кода внутри одного процесса: это модули и `dependsOn` ([module.md](./module.md)).

## 2. Что уже держит проверка

Пока `bun run check` монорепо зелёный, границы ниже держит машина — `arch:check` и тесты:

| Граница | Правило | Что это даёт выносу |
|---|---|---|
| пакет реализации не видит соседей, сборку и раннеры | ARC-06 | пакет уносится без чужого кода исполнения |
| чужой модуль — только `contract` и только из `dependsOn` | ARC-04 | сервису нужны контракты зависимостей, а не весь домен (D-28) |
| раннер-процесс не видит реализаций | ARC-08 | транспорт меняется, модуль — нет |
| один UoW — один модуль | MAN-13 | нет транзакции через границу сервиса |
| каждый импортируемый пакет объявлен в `package.json` единицы | ARC-14 | `package.json` вынесенного пакета полон |
| между единицами — имя пакета и `exports`, помощники тестов — через `/testing` владельца | ARC-15 | нет относительных путей к соседям, в том числе в тестах |
| `package.json` единиц платформы приложения не объявляет реализации и раннеры; вход графа не доходит до реализаций | ARC-16 | контракты и граф строятся без реализаций (GR-02) |

Не проверяется машиной: модуль владеет своим хранилищем (ревью), `extends` в `tsconfig` к корню монорепо, импорт через `require()` и алиасы `paths` — полный список «Чего машина не проверяет» в D-108.

## 3. Шаги

1. **Проверка — машина.** `bun run check` зелёный: ARC-04/06/08, ARC-14…16, MAN-13 чисты. Красный — сначала граница, потом вынос.
2. **Хранилище — руками и ревью.** Данные модуля читает и пишет только его репозиторий; файлы и таблицы модуля переезжают вместе с сервисом. Чтение чужих данных мимо фасада машина не ловит.
3. **Платформа приложения — руками.** Сервис зависит от `@<scope>/kernel` и `@<scope>/domain` (контракты). В другом репозитории их публикуют в приватный реестр: git-зависимость Bun берёт репозиторий целиком, не подпапку (D-108, «Цена»).
4. **Своя сборка — руками.** Сервис из одного модуля — то же приложение с одним модулем (D-28, D-106): своя сборка (`runners/assembly` сервиса) строит `AppContext`, хранилище модуля, `ApiApp` и резолвер `Caller` — по образцу [app.md](./app.md). Каждому модулю из `dependsOn` `ApiApp` нужна фабрика в том же процессе: фасада к удалённому модулю нет (§4).
5. **Свой раннер-процесс — руками.** Вход сервиса — транспорт по контракту команды: `POST /api/<module>`, тело `{ uc, input, meta }`, ответ — сериализованный `Result` ([transport.md](../reference/transport.md) §2). Реализаций транспорта в пакете нет; `Caller` и `Trace` раннер переводит в токен и заголовки и обратно (D-28).
6. **Вызовы из монолита — руками.** Раннеры и UI монолита вызывают сервис через `ModuleApi` (`dmg-core/app`) над своим `CommandTransport`: вызывающий код тот же, ответ восстанавливается по Def UC ([transport.md](../reference/transport.md) §4). Модули монолита, зависящие от вынесенного, фасад к нему не получат — это шов исполнения (§4).
7. **События — руками.** Шина — порт `EventBus`; в пакете только `InProcEventBus`. Доставку между процессами (брокер, outbox/inbox) пишет проект; реакции уже идемпотентны и публикуются через outbox (D-28).
8. **`tsconfig` — руками.** `extends` к корню монорепо — не импорт, проверка его не видит: у вынесенного пакета свой `tsconfig.json`.
9. **Тесты — машина в монорепо, руками после.** Тесты пакета остаются при нём; помощники соседей — только через их `/testing` (ARC-15). Прогона тестов из каталога пакета как проверки выноса нет: в монорепо пакеты всё равно разрешаются через корень.

## 4. Чего в пакете нет

Шов исполнения удалённого модуля — `DEBT-5` реестра долга пакета: `ApiApp` строит фасад зависимости только из модуля своего процесса, удалённого подключения (фасад над `ModuleApi`), HTTP-транспорта и межпроцессной доставки событий нет. Триггер — первый вынос модуля или HTTP-транспорт в пакете; тогда же сценарий GR-01 получает статус «проверен вживую».

## 5. Модуль на другом языке (GR-02)

- **Источник — платформа приложения.** Граф (`bun run graph` → `graph.json`) и контракты модуля (`OPTIONS /api/<module>`: JSON Schema входа и выхода UC, ошибки, политика) строятся из `kernel` и домена без реализаций — это держит ARC-16 и ARC-02.
- **Что реализует сервис на другом языке:** контракт команды и ответа ([transport.md](../reference/transport.md) §1–2), события по Def с payload по схеме, ошибки с `code` и `kind` из контракта. `backend/app` и `dmg-core/app` ему не нужны.
- **Руками:** генерации кода для другого языка из графа нет, проверки реализации на соответствие контракту — тоже; Policy и доменные правила модуля переносятся вместе с реализацией.

## 6. Чеклист правил

- ARC-04, ARC-06, ARC-08, MAN-13 — граница модуля и раннеров чиста до выноса.
- ARC-14 — каждый импорт объявлен; `devDependencies` — только в тестовом коде.
- ARC-15 — между пакетами только имя и `exports`; помощники тестов — через `/testing`.
- ARC-16 — `platform/*` не объявляет реализации и раннеры.

## 7. Типичные ловушки

- Установка `--linker hoisted` или зависимость корня монорепо — необъявленный импорт разрешается, а после выноса нет. ARC-14 ловит его по спецификатору: красный `arch:check` перед выносом не пропускай.
- Алиас `paths` в `tsconfig` на `src` соседнего пакета — импорт мимо `exports` разрешается, ARC-15 молчит (D-108).
- Общая папка помощников тестов в корне монорепо — ARC-15; помощник переезжает в `/testing` пакета-владельца.
- Модуль монолита ждёт фасад вынесенного модуля — `ApiApp` бросает «фабрики … в приложении нет»: шов `DEBT-5`, вызов — через `ModuleApi` из раннера или событие.

# Расширение `gen` и `sync` пакетом-поставщиком — гайд

**Назначение:** как пакет-поставщик (UI, адаптер, размещение) доставляет проекту свои скилы и роли агентов (`dmg-core sync`) и добавляет свои виды заготовок в `dmg-core gen` — снаружи `dmg-core`, только через публичные входы. Образец — фикстура `src/testing/example-provider/`: скил, роль и вид `example-unit`. Расширение графа и проверок — отдельный гайд ([graph-extension.md](./graph-extension.md)); пакет обычно делает и то и другое.

---

## 1. Когда применять

- Пакет несёт знание для агентов (скил «как писать на моём слое», роль) — доставка `sync` (§3).
- Пакету нужны свои заготовки (`dmg-core gen <вид> …`): каталог и пакет единицы своего слоя — `gen` (§4).
- Домен модулей — не поставщик: его заготовки — виды самого `dmg-core` ([naming.md](../reference/naming.md) §5).

## 2. Подключение

Проект перечисляет пакеты в `.dmg/config.json`; `dmg-core` подключён всегда и в списке не перечисляется:

```json
{
  "providers": ["example-provider"],
  "layers": {
    "example-unit": { "dir": "units/{m}/src", "package": "@acme/{m}-unit" }
  }
}
```

- **Вход пакета — `<пакет>/dmg-core`.** Пакет объявляет его в `exports["./dmg-core"]`. Корень поставщика — ближайший над входом `package.json` с тем же `name`; пакет поставляет `skills/` и `agents/roles/` из этого корня. Пакет не найден (нет входа) — отказ «пакет не найден от корня проекта» в `sync`, `sync --check` и `gen`; ничего не записано.
- **Порядок `providers` значим** — по нему идут сообщения о конфликтах и порядок видов в подсказке `gen`.
- **`layers`** — места слоёв поставщиков: `{ "<слой>": { "dir": "<шаблон с {m}>/src", "package"?: "@scope/x-{m}" } }`. `package` — только если `dir` оканчивается на `/src`; `{m}` в `package` — парой с `{m}` в `dir`. Те же каталоги проект передаёт проверяющему слоёв в `ArchApp.layers` ([graph-extension.md](./graph-extension.md), шаг 5; `GenLayout.layerDirs()`). Неизвестное поле конфига — отказ.

## 3. `sync`: скилы и роли

Структура пакета-поставщика, как у `dmg-core`:

```
<пакет>/
  package.json             name, version (обязателен), exports["./dmg-core"]
  skills/<скил>/SKILL.md   как у dmg-core
  agents/roles/<роль>.md   формат — agents/README.md
```

Правила:

1. **Общий блок ролей — только у `dmg-core`.** Файл `agents/common.md` у поставщика — ошибка поставки. К ролям поставщика `sync` дописывает общий блок `dmg-core`, как к своим.
2. **`version` в `package.json` обязателен** — без неё отказ.
3. **Метка копии — `<!-- <пакет>@<версия>: сгенерировано … -->`.** У копий `dmg-core` формат прежний (`dmg-core@…`). Рост версии поставщика — копия «устарела», `sync` обновляет; смена владельца копии показывается как `устарела (<пакет>@<версия> → <пакет>@<версия>)`. Программный разбор — `Marker.of` / `Marker.strip` (`dmg-core/cli`): `strip` снимает метку любого пакета.
4. **Имя скила или роли — у одного владельца.** Совпадение между поставщиками или с `dmg-core` — отказ с обоими владельцами в порядке `providers` («скил «x» есть у kit-a и kit-b»); `sync` и `sync --check` ничего не пишут; `gen` тоже отказывает — он собирает тот же набор пакетов. Совпадение считается по всему содержимому пакетов, до фильтров `names`.
5. **Пакет убран из `providers` — его копии без источника (`stale`).** `sync --check` сообщает о них, `sync` удаляет. Файл проекта на месте копии (без метки) `sync` не трогает — ошибка.
6. **Явные `skills.names` / `roles.names` скрывают нового поставщика.** `init` пишет в конфиг списки по умолчанию; после этого скилы и роли пакета, добавленного в `providers` позже, в `names` не попадают — предупреждения нет. Добавь их имена в `names` вручную (или убери поле — «всё из поставки»). Имя в `names`, которого нет ни у одного пакета, — отказ.
7. **Вставка в файл инструкций (`instructions`) — только `dmg-core`**: блок ссылается на `node_modules/dmg-core/llms.txt`.
8. **`roles.refs` работают и для ролей поставщика**: блок «Знания проекта» — в копии роли поставщика, метка копии — поставщика; роль должна доставляться (`roles.names`).

Код: тип `ProviderPackage` (поиск и чтение пакета; снаружи — только тип), `PackageSet` (объединение `dmg-core` и поставщиков), `CliConfig(PackageSet)` — `dmg-core/cli`.

## 4. `gen`: виды поставщика

### Экспорт

Вход `<пакет>/dmg-core` экспортирует именованный `gen` (не `default`):

```ts
import { GenError, type GenPlan, type GenProvider } from 'dmg-core/gen';

export const gen: GenProvider = {
  kinds: [{ name: 'example-unit', usage: '<модуль>', plan }],
};
```

Пакет без `gen` — виды не объявляет (только скилы и роли). `gen` не объект вида `{ kinds: [...] }` — ошибка поставки.

### Вид — `GenProviderKind`

| Поле | Смысл |
|---|---|
| `name` | имя вида, kebab-case (`a-z`, `0-9`, дефисы); повтор внутри пакета — ошибка |
| `usage` | аргументы вида для подсказки: `<модуль>`; пустая строка — аргументов нет |
| `plan(args, { layout })` | план файлов; `args` — позиционные аргументы после имени вида |

- **`plan` синхронный** и возвращает `GenPlan` (`{ files, edits, dependencies?, notes? }`). `Promise` вместо плана — отказ «вернул не план»; но отклонённый `Promise` — дефект поставщика, не обрабатывается ядром.
- **Флаги — у ядра.** `--write`, `--dry-run`, `--adopt` разбираются до поиска вида и не попадают в `args`; своих опций у вида нет. Лишние аргументы и их формат вид проверяет сам.
- **План применяет ядро** тем же `applyPlan`, что и для видов `dmg-core`: без `--write` — dry-run (печатает файлы, ничего не пишет), с `--write` — пишет и правит `package.json` корня по `dependencies`, `--adopt` пропускает существующие файлы («Пропущен: … (уже есть)»). Первая строка вывода — `Вид «<имя>» — <пакет>, слои: …` (без `layers` — `слои не заданы (layers в .dmg/config.json)`).
- **Ошибка ввода — `GenError`** из `dmg-core/gen`: ядро печатает «Ошибка: <текст>» и возвращает код 1, ничего не записано. `GenError` узнаётся по `name` (`GenError.is`), не по `instanceof`.
- **Признаки, не `instanceof`.** У поставщика может быть своя копия `dmg-core` (другой `node_modules`), поэтому ядро проверяет форму вида и плана по признакам, и вид не должен проверять `layout` через `instanceof`.

### Раскладка — `layout`

`GenContext.layout` — `GenLayout` проекта:

| Член | Что даёт |
|---|---|
| `layout.root` | корень проекта, как его передал вызывающий: у CLI — `'.'` (пути плана относительны каталогу запуска), в тесте — свой каталог; корневой `package.json` — `join(layout.root, 'package.json')` |
| `layout.layerNames()` | имена слоёв из `layers` в порядке конфига |
| `layout.layerDir(слой, модуль)` | каталог слоя для модуля, `{m}` подставлен; слоя нет в `layers` — `GenError` |
| `layout.layerPackage(слой, модуль)` | `{ dir, name, root }` пакета workspaces слоя; нет `package` у слоя — `undefined` |

Пути в плане — абсолютные (`join(layout.layerDir(…), …)`). Виду поставщика не нужны `gen.kernel`, `gen.assembly`, `gen.appDef`: ядро не требует их для видов поставщиков, и вид не вызывает `layout.dirs()` (он бросает при отсутствии этих ключей).

### Каталог видов и конфликты

- Виды `dmg-core` и поставщиков собираются в один каталог до разбора команды; у каждого имени — один владелец. Вид поставщика с именем вида `dmg-core` или двух поставщиков между собой — отказ «вид «x» есть у … и …» (в порядке `providers`).
- Неизвестный вид или пустая команда — подсказка: свои виды `dmg-core`, затем блок «Виды поставщиков» со строкой `<вид> <usage> — <пакет>` на вид. Без поставщиков вывод прежний.
- **Вход импортируется только в `gen`.** Сломанный вход (не загружается, `gen` неверной формы, имя не kebab-case) ломает `gen` с сообщением, называющим пакет, но не `sync` и не `sync --check`: они чужой код не исполняют.

## 5. Образец

Фикстура `src/testing/example-provider/`:

- `package.json` — `name`, `version`, `exports["./dmg-core"]`;
- `dmg-core.ts` — `export const gen`: вид `example-unit <модуль>` создаёт `index.ts` в `layout.layerDir('example-unit', модуль)` и, если у слоя есть `package`, его `package.json` и зависимость в `package.json` корня; нет аргумента — `GenError`;
- `skills/example-skill`, `agents/roles/example-author.md`.

Относительные импорты `../../gen/index` в фикстуре допустимы только внутри репо `dmg-core` (её `package.json` отрезает `imports` пакета); настоящий поставщик импортирует `dmg-core/gen`. Тесты образца — `src/cli/dmg-core-cli.providers.test.ts` (доставка, конфликты, `stale`), `src/gen/main.test.ts` (вид), `src/gen/gen-kinds.test.ts` (каталог видов), `src/cli/provider-package.test.ts` (форма входа).

## 6. Проверка

- В проекте-потребителе: `providers` и `layers` в `.dmg/config.json`, `bunx dmg-core sync` (копии с меткой пакета), `bunx dmg-core gen <вид> <аргументы>` (dry-run), затем с `--write`.
- Dry-run печатает план и ничего не пишет — сначала прочитай его.

## 7. Подводные камни

- **Явные `names` после `init`** скрывают скилы и роли нового поставщика молча (§3, п. 6).
- **Конфликт имён скилов и ролей ломает и `gen`**, не только `sync`: набор пакетов общий.
- **Асинхронный `plan`** — отказ формы; готовь данные до `plan` или читай файлы синхронно.
- **`instanceof` на `GenError`/`GenLayout`** ломается между копиями пакета — `GenError.is`, признаки.
- **Сломанный вход блокирует все виды `gen` проекта**, а не только свой: ошибка называет пакет; `sync` продолжает работать.
- **Кэш резолвера Bun:** промах поиска входа в каталоге кэшируется на процесс — пакет, установленный после первого промаха, в том же процессе не находится; поставь пакет до запуска.
